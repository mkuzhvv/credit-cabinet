# Классификатор риска на синтетических заявках

Пробный автономный компонент для хакатона. Генерирует вымышленные компании и заявки под пять продуктов из `../llm/products.json`, обучает CatBoost, сравнивает его с логистической регрессией и выдаёт результат для одной заявки. Ollama, платные API и GPU не нужны. Путь к каталогу можно переопределить переменной окружения `CREDIT_PRODUCTS_PATH`.

**Это модель симулятора, а не проверенный банковский скоринг.** Данные о финансовых показателях и связи между ними придуманы автором. Модель воспроизводит эти предположения. Высокая метрика на сгенерированных данных не подтверждает точность на реальных клиентах. SBA-датасет в этом эксперименте не используется.

## Что уже находится в папке

- `generate.py` — воспроизводимый генератор с фиксированным seed.
- `train.py` — обучение, калибровка, baseline и независимые тестовые выборки компаний.
- `common.py` — признаки, общие преобразования и отдельные правила продуктов.
- `score.py` — функция `score(application)` и запуск на JSON.
- `examples/` — два вымышленных профиля для проверки.
- `data/` — созданные CSV и описание происхождения.
- `artifacts/` — обученная модель, калибратор, метрики и предсказания теста.
- `test_scoring.py` — проверки контракта, разбиения, воспроизводимости и продуктовых ограничений.

## Запуск

Из корня репозитория:

```sh
cd ml/scoring
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock.txt
.venv/bin/python generate.py
.venv/bin/python train.py
.venv/bin/python -m unittest -v
.venv/bin/python score.py examples/healthy.json
.venv/bin/python score.py examples/risky.json
```

Для созданной здесь среды первые две команды уже выполнены. Проверено на Python 3.12, CPU, с четырьмя потоками обучения. Для Windows путь к Python в среде — `.venv\Scripts\python.exe`. `requirements.txt` фиксирует прямые зависимости, `requirements.lock.txt` — все установленные версии. Данные и бинарные артефакты исключены из Git, но воспроизводятся командами выше.

## Что генерируется

По умолчанию 12000 вымышленных компаний с тремя заявками на компанию: 36000 строк. Отдельно создаются 4000 стресс-примеров от других компаний. Нет реальных имён, ИНН, адресов и персональных данных.

Суммы, сроки, ставки и минимальный возраст бизнеса взяты из каталога команды. Распределения выручки, расходов, денежных остатков, просрочек и коэффициенты риска придуманы специально для прототипа. Часть заявок намеренно нарушает продуктовые требования — для проверки логики отказа.

Одна компания целиком попадает в одну из выборок: примерно 60% train, 15% selection для остановки обучения, 10% calibration, 15% test. Пересечений компаний нет. Это случайное разделение компаний, **не проверка на будущих периодах**: реальных временных данных здесь нет.

## Признаки запроса

| Поле | Значение |
| --- | --- |
| `product_id` | ID выбранного продукта из каталога |
| `business_age_months` | Возраст бизнеса в месяцах |
| `monthly_revenue_rub` | Среднемесячная выручка за последние 12 полных месяцев; для более молодого бизнеса в этом эксперименте среднее за доступные полные месяцы |
| `monthly_expenses_rub` | Среднемесячные операционные расходы за тот же период, без кредитных платежей |
| `existing_monthly_payments_rub` | Платежи по уже существующим кредитам в месяц |
| `cash_balance_rub` | Доступные собственные денежные средства на дату заявки |
| `inflow_mean_3m_rub` | Среднемесячные поступления на счёт за последние 3 месяца |
| `revenue_volatility` | Коэффициент вариации месячной выручки: стандартное отклонение / среднее за доступный период до 12 месяцев |
| `revenue_change_6m` | Относительное изменение выручки за 6 месяцев, например −0.2 = падение на 20%; здесь это непосредственно заданный синтетический показатель |
| `late_payment_days_12m` | Максимальная длительность просрочки за последние 12 месяцев, дни |
| `requested_amount_rub` | Запрошенная сумма; у линий и овердрафта — запрошенный лимит |
| `requested_term_months` | Срок кредита или одного транша; у овердрафта значение 1 означает 30 дней |

Для правил также нужны `legal_form`, `registered_in_russia`, `current_overdue`. `purpose_confirmed=true` означает, что вызывающая сторона уже подтвердила соответствие цели продукту. Иначе требуется дополнительное рассмотрение. Для овердрафта дополнительно передаются `has_bank_account`, `regular_inflow_months`, `expected_inflow_days`; для госконтракта — `has_signed_44fz_contract`.

В текущем чате и тестовой анкете всех этих полей ещё нет. Это предлагаемый контракт нового модуля; реальные значения должен собирать бэкенд или получать из подключённых источников. LLM не должна придумывать отсутствующие показатели. Значения заполняются синтетически только в демонстрационных примерах.

Для молодых компаний источники расчёта динамики и волатильности требуют отдельного согласования с командой. Они пока моделируются генератором как доступные сведения. Это упрощение, а не перенос определения из существующего справочника полей.

## Откуда берутся метки

Модель предсказывает `simulated_default`, а не решение банка. Это случайное событие невозврата за период `min(requested_term_months, 12)` месяцев. Срок одного транша не равен сроку всей линии. Для овердрафта период равен 30 дням. Предсказания разных продуктов с разным горизонтом нельзя напрямую сравнивать как единую 12-месячную вероятность.

Сначала считаются условные показатели:

```text
margin = (revenue − expenses) / revenue
cash_buffer = cash / revenue
planning_burden = (existing_payments + amount / term + amount × annual_rate / 12) / revenue

z = −3.1
    + 5 × min(planning_burden, 2)
    + 3 × (0.2 − margin)
    + 1.2 × volatility
    − revenue_change_6m
    + 0.018 × late_payment_days
    − 0.65 × min(cash_buffer, 2)
    + 0.5 × indicator(business_age < 12)
    + hidden_risk

p_annual = sigmoid(clip(z, −12, 12))
p_observation = 1 − (1 − p_annual) ** (min(term, 12) / 12)
simulated_default ~ Bernoulli(p_observation)
```

`hidden_risk` — общий для компании случайный фактор Normal(0, 0.65). Он создаёт неопределённость и не передаётся модели. Точная вероятность симулятора и скрытый фактор сохраняются отдельно в `simulator_audit.csv` для аудита; они не входят в обучающие признаки.

`planning_burden` — условная нагрузка для генерации и модели, **не реальный платёж по графику**. Для линий упрощённо предполагается немедленная выборка всей суммы лимита. Повторные транши, сезонный календарь и движение денег по госконтракту не моделируются. Метки гипотетически генерируются и для заявок, которые затем не проходят правила, а не выдаются за наблюдённые результаты отказанных клиентов.

Стресс-выборка имеет более высокие расходы, меньше ликвидности, отрицательную динамику и дополнительный скрытый сдвиг риска +0.45. Она проверяет чувствительность к сдвигу внутри того же искусственного мира. Это не независимое подтверждение самой формулы риска.

## Как получается решение

Сначала обычный код проверяет ограничения каталога. При нарушении выдаёт `decline`, не запуская ML. Затем считается `synthetic_default_probability` и применяется условная политика:

- до 0.15 включительно — `approve`, если нет непроверенных требований;
- между 0.15 и 0.45 — `review`;
- от 0.45 — `decline`;
- непроверенные условия также блокируют автоматическое `approve`.

Эти пороги — авторские допущения для показа, а не банковская политика и не результат оптимизации реальных убытков. `approve` — статус прототипа, а не обещание выдачи средств.

Для линии на госконтракт всегда остаётся дополнительная проверка: формула вычета аванса в каталоге не уточнена, дата возврата и целевые расходы не представлены полным контрактом. Для возобновляемой линии дополнительно проверяется окончание линии. Полноту финансовых документов и все внешние проверки этот модуль не подтверждает.

При изменении каталога модель отказывается давать ML-предсказание до повторной генерации и обучения: контрольная сумма хранится в артефактах.

## Метрики

В `artifacts/metrics.json` сравниваются постоянный прогноз, логистическая регрессия, CatBoost до и после калибровки. Считаются ROC-AUC, Average Precision, Brier score и log loss на test и stress, а также по продуктам. Модель и калибровка обучаются без доступа к этим тестовым меткам. Average Precision не равна трапецеидальной площади под PR-кривой.

Эти значения измеряют воспроизведение симулятора. Прежде чем применять модель к реальным компаниям, нужны реальные исходы, согласованные определения признаков, оценка на отложенных периодах, калибровка и проверка принятой политики решения.
