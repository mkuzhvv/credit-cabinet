# Скоринг по формальным правилам

Обучение, синтетический датасет, CatBoost и файлы весов удалены. Вместо них — проверка денежных потоков для пяти продуктов. `ml/llm` сохранён отдельно и не участвует в принятии решения.

Это политика MVP с выбранными коэффициентами. Она проверяет выполнение формулы и не оценивает вероятность невозврата или качество реального кредитования.

## Запуск

Python 3.12, без GPU и Ollama. Из папки `ml/scoring`:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
python server.py --host 127.0.0.1 --port 8000
```

Из другого терминала:

```bash
curl http://127.0.0.1:8000/health/ready
curl -H 'Content-Type: application/json' \
  --data-binary @examples/working_capital.json \
  http://127.0.0.1:8000/internal/v1/assessments
```

Одна заявка без сервера:

```bash
python score.py examples/working_capital.json
python score.py examples/insufficient_cash.json --explain
```

Первая команда выводит ровно HTTP-ответ. `--explain` дополнительно показывает `decision`, `reasonCodes`, платежи и остатки. Источники примеров — контракт и ручные граничные сценарии, это не датасет для обучения.

Локальные проверки (папка `tests/` остаётся на компьютере и исключена из минимальной Git-версии):

```bash
python -m unittest discover -s tests -t . -v
```

При необходимости контейнер: `docker build -t credit-scoring .`, затем `docker run --rm -p 8000:8000 credit-scoring`. Контейнер не содержит Ollama. Сервис предназначен для внутренней сети Java; авторизацию/доступ извне обеспечивает инфраструктура.

## Что передаёт бэкенд

Контракт: [OpenAPI 0.4.0](contracts/scoring.openapi.yaml), схема признаков **`"4"`**. Полный JSON для каждого продукта — в `examples/`.

- `GET /health/live` → `{"status":"UP"}`.
- `GET /health/ready` → `status`, `modelVersion`, `featureSchemaVersion`, `supportedProductCodes`.
- `POST /internal/v1/assessments` → оценка одной заявки за бюджет 10 секунд.

Структура входа прежняя: `assessmentId`, `applicationId`, `featureSchemaVersion`, `features`. Все прежние поля сохраняются. Новое обязательное поле: **`features.cashBalance`** — свободные собственные деньги до нового финансирования. Деньги передаются строками с двумя знаками, например `"1000000.00"`, не JSON-числами. Неприменимые продуктовые поля передаются как `null`.

Ответ содержит ровно четыре поля:

```json
{
  "assessmentId": "8de449ef-d46c-4a0d-b108-e37d3b00bd94",
  "featureSchemaVersion": "4",
  "modelVersion": "rules-cashflow-v1-<fingerprint>",
  "riskScore": 0.0
}
```

`<fingerprint>` здесь обозначает фактический отпечаток, который нужно прочитать из readiness. `modelVersion` сохранён ради совместимости, обученной модели нет.

**`riskScore = 0.0` — правила пройдены; `1.0` — нарушены. Это бинарный индекс, не вероятность.** Для прежнего сравнения Java закрепляет `riskCutoff = 0.5`: значение меньше порога означает одобрение. Значений между 0 и 1 сервис не выдаёт.

Переход с прежнего скоринга требует изменений Java:

1. Добавить `cashBalance` из подтверждённых данных в DTO признаков и снимок заявки; сохранять источник/дату. Если значение вводит пользователь, согласованно добавить его в публичный контракт Java и форму фронта.
2. Установить `featureSchemaVersion = "4"`, новую `policyVersion`, `riskCutoff = 0.5`; закрепить конкретный `expectedModelVersion` из readiness. Не принимать любую версию автоматически при каждом вызове.
3. Проверять совпадение `assessmentId`, схемы и версии ответа. Технические ошибки переводить в `TECHNICAL_HOLD`, не в отказ.
4. Использовать одну версию продуктового каталога в Java и Python. После изменения условий перезапустить сервис и обновить закреплённую версию правил.

Схема `"3"`, отсутствующий остаток и неизвестные обязательные данные дают `422`, а не подстановку нуля. `riskScore = 1.0` возвращается с HTTP `200` только для корректной заявки, не прошедшей денежную политику.

Ошибки — `application/problem+json`: `400 MALFORMED_REQUEST`, `422 INVALID_FEATURES` с ошибками полей, `503 MODEL_NOT_READY`, `500 INFERENCE_FAILED`. Последние два кода сохранены для совместимости. Каждый ответ содержит `X-Request-Id` и `Cache-Control: no-store`.

Фронт работает через Java, Python напрямую не вызывает. LLM продолжает объяснять продукты и поля. Решение принимает бэкенд с результатом формулы; ассистент не обещает одобрение.

## Формула и семь величин

| Величина | Источник |
|---|---|
| I, среднемесячные поступления | `averageMonthlyInflow` |
| E, все среднемесячные расходы | `averageMonthlyOutflow`, уже включая текущие платежи по долгам |
| B, свободный остаток | `cashBalance` |
| A, сумма / общий лимит | `amount` |
| n, срок фактического погашения | Кредит / выбранный транш / 30 дней овердрафта |
| T, возраст бизнеса | `businessAgeMonths` |
| D, текущая просрочка | Проверенный `creditHistory` |

Ставки и условия берутся из `catalog.json`. Срок лимита отличается от срока долга: у овердрафта `termMonths=12`, но возврат за 30 дней; у возобновляемой линии `termMonths=24`, транш 3–6 месяцев.

```text
F = 0.90 × I − E
C₀ = B
Cₜ = Cₜ₋₁ + F − 1.30 × Pₜ
R = 1.00 × E

Одобрить, если обязательные условия выполнены,
возраст бизнеса достаточен, текущей просрочки нет
и min(C₀, …, Cₕ) ≥ R.
```

`Pₜ` — сценарный платёж нового кредита в месяце t; h — горизонт проверки. В `policy.json` настраиваются стресс поступлений, запас платежей и резерв расходов. Эти коэффициенты выбраны для MVP, не получены из статистики и не являются нормативами банка.

`monthlyDebtPayment` не вычитается повторно, он уже входит в E. Новый кредит не добавляется к свободному остатку B. Заёмные или недоступные деньги не являются B.

Для `NO_HISTORY` четыре показателя отчёта остаются `null`: статус не превращается в положительную историю и не освобождает от проверки ликвидности. Прошлые погашенные просрочки и общая задолженность сохраняются в запросе, но не получают придуманных статистических весов. Если кредитный источник недоступен или неполон, Java не должна вызывать скоринг с фиктивными данными.

Расчёт — `Decimal` с точностью 50 знаков. Платежи округляются вверх до копейки; решение принимается по неокруглённым остаткам. Равенство резерву проходит проверку. Отображение остатков округляется вниз, отдельно от решения.

## Платёжные сценарии и ограничения

| Продукт | Сценарий для формулы |
|---|---|
| Оборотный, длительный | Аннуитет на весь срок, месячная ставка = годовая / 12 |
| Овердрафт | Полный лимит + проценты за 30/365; повтор полного цикла каждый месяц срока лимита |
| Возобновляемая линия | Полные последовательные транши, равные доли основного долга + проценты на остаток; горизонт 24 месяца |
| Госконтракт | Полная выборка, ежемесячные проценты, весь основной долг в конце срока |

Для аннуитета `P = A×i / (1−(1+i)^(−n))`, при ставке 0 — `A/n`. Для дифференцированного платежа основная доля `A/n`, проценты — на остаток перед платежом. Последний транш сокращается до конца линии; при остатке меньше 3 месяцев новая выборка не моделируется.

Это **консервативные сценарии оценки**, не фактический график обслуживания кредита. Проценты месячных сценариев рассчитаны как годовая ставка / 12; овердрафта — за 30 дней по базе 365. Внутримесячные кассовые разрывы и сезонность не учитываются. Будущие дополнительные доходы проекта и отдельная ожидаемая оплата госконтракта не прибавляются к I без подтверждённого прогноза. Поэтому положительное решение не гарантирует возможность обслуживать реальный кредит.

Проверки сумм, дат и продуктовых полей выполняются до формулы. Например, превышение лимита овердрафта `30% × I` или госконтракта `70% × (стоимость − аванс)` — ошибка `422`, не отказ по ликвидности. При `LONG_TERM` положительный бюджет обязателен, но правило `amount ≤ projectBudget` не вводится.

Java по-прежнему проверяет ИП/ООО, регистрацию в РФ, расчётный счёт, регулярность поступлений и назначение госконтракта по 44-ФЗ: этих подтверждений в запросе скоринга нет. Порядок `NEEDS_INFO` для подтверждения нулевых поступлений также остаётся у Java.

## Файлы и версии

- `engine.py` — формула и сценарии платежей.
- `validation.py` — JSON Schema, продуктовые пределы и календарные проверки.
- `server.py` — HTTP-контракт Java → Python.
- `score.py` — локальная проверка одной заявки.
- `catalog.json`, `policy.json` — условия и параметры.
- `contracts/` — OpenAPI, производные JSON Schema, источник исходного контракта.
- `examples/` — интеграционные примеры; локальная папка `tests/` содержит проверки и исключена из Git.

Базовый контракт взят из `main` коммита `c5efe263f89f1a3b24eb8bb53b22851e65255e54`, затем обновлён до схемы 4. Каноническая копия: `docs/contracts/scoring.openapi.yaml`; локальная копия должна совпадать. `contracts/schemas.json` содержит те же схемы с преобразованными `$ref` в `$defs` и используется без YAML-зависимости при запуске.

Отпечаток `modelVersion` включает исходники расчёта/валидации, каталог, политику и схемы. Конфигурация читается один раз до readiness. Альтернативные файлы: `python server.py --policy /path/policy.json --catalog /path/catalog.json` либо `SCORING_POLICY_PATH`, `SCORING_CATALOG_PATH`. Изменение файлов требует перезапуска; старый закреплённый `expectedModelVersion` после изменения условий не подходит.

В Git нужны исходники, конфигурация, контракты, Dockerfile, зависимости, примеры и документация по запуску. `.venv`, кэши, логи, локальные тесты, отчёты и результаты прежнего обучения исключены. Старый скоринг сохранён вне репозитория в папке `../scoring-before-rules-20261024` относительно корня `credit-cabinet`.

Локальные тесты подтверждают расчёты и HTTP-контракт Python. Сквозную интеграцию Java → Python → итоговая заявка нужно проверить после обновления Java; работающий Java-бэкенд в этой ветке отсутствует.
