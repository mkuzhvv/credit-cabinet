# Бэкенд

Java 21, Spring Boot 4.1.2, Maven Wrapper 3.9.16. Корневой пакет — `com.creditcabinet`.
Реализованы PostgreSQL/Flyway, форматы и ошибки API, демосессия, каталог, идемпотентность, заявки с автоматическим рассмотрением и восстановлением, а также диалоги помощника через Spring AI/Ollama. Отчёт приёмки и подробное объяснение кода: [BACKEND_WALKTHROUGH.md](../BACKEND_WALKTHROUGH.md).

## Локальный запуск

1. Запустить Docker Desktop.
2. Из корня репозитория поднять БД:

```powershell
docker compose -f docker/compose.db.yaml up -d --wait
```

3. Запустить конфигурацию `Backend` в IDEA либо из `backend/`:

```powershell
.\mvnw.cmd spring-boot:run
```

На Linux/macOS: `sh ./mvnw spring-boot:run`. Нужен JDK 21: в IDEA выбрать его для проекта и Maven; для терминала задать `JAVA_HOME` на свой каталог JDK.

База `credit_cabinet` доступна на `localhost:5432`, пользователь `credit_cabinet`, пароль не нужен. Настройки уже заданы в `application.yaml`, `.env` и ручная настройка подключения не требуются. При необходимости подключение можно переопределить через `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.

## Схема и данные

Flyway применяет `V1__create_schema.sql` (10 таблиц приложения), `V2__seed_demo_identity.sql` (две синтетические компании и два представителя) и `V3__seed_credit_products.sql` (пять демонстрационных продуктов). Повторный запуск не пересоздаёт таблицы и не дублирует начальные данные. Применённые миграции не переписываются; следующие изменения оформляются новой версией.

Hibernate использует `ddl-auto=validate`, Open Session in View отключён. Компания, представитель и продукты читаются через JPA.

JSONB используется для снимков рассмотрения и кредитной истории, результата, сохранённых ответов команд и метаданных чата. Связи, текущая форма, состояния и поля очереди остаются обычными столбцами.

## Сборка и проверки

Из `backend/`: `.\mvnw.cmd package` (Windows) или `sh ./mvnw package` (Linux/macOS). Сборка не поднимает тестовые контейнеры. `HttpContractTest` проверяет только HTTP-слой без подключения БД и моделей; отдельно: `.\mvnw.cmd -Dtest=HttpContractTest test`.

Минимальная проверка этапа 01: контейнер БД готов, Java запускается, Flyway применяет миграцию без ошибок. Проверки бизнес-правил добавляются вместе с соответствующей логикой; полный интеграционный прогон после каждого изменения не требуется.

Команды остановки БД — в [docker/README.md](../docker/README.md). Структура таблиц — в [docs/DATABASE_SCHEMA.md](../docs/DATABASE_SCHEMA.md), форматы API — в [docs/contracts/](../docs/contracts/README.md).

## Общий слой API (этап 02)

Каждый запрос получает серверный UUID в `X-Request-Id`; он же включается в ошибку и логи. Заголовок клиента не заменяет серверный идентификатор. Ответы `/api/v1/` имеют `Cache-Control: no-store`.

Ошибки MVC возвращаются как `application/problem+json` с `type`, `title`, `status`, `code`, `requestId`, при необходимости `errors` (до 30 полей). JSON с неверной структурой/типами, неизвестные поля и некорректные UUID дают `400 MALFORMED_REQUEST`; Bean Validation — `422 VALIDATION_FAILED`; непредвиденная ошибка — `500 INTERNAL_ERROR` без технических подробностей в ответе. Стандартные статусы 404/405/406/415 сохраняются с кодами `NOT_FOUND`/`METHOD_NOT_ALLOWED`/`NOT_ACCEPTABLE`/`UNSUPPORTED_MEDIA_TYPE`.

Денежные поля HTTP DTO помечаются `@MoneyJson`: внутри `BigDecimal`, снаружи строка `"150000.00"`. Допустимый диапазон `0.00`–`999999999999.99`; лишние знаки не округляются. `null` разрешается самим форматом, обязательность задаётся отдельно через Validation. Формат применяется только к отмеченным полям, не ко всем `BigDecimal`.

Swagger UI: `/swagger-ui/index.html`, генерируемая схема: `/v3/api-docs`. Метаданные API — версия 0.5.0; нормативный YAML — `docs/contracts/backend.openapi.yaml`. Доступны операции сессии, каталог, черновики заявок, submit и retry. Для POST/PUT в Swagger скопировать токен из GET `/api/v1/csrf` в Authorize → `CsrfToken`; после входа получить новый токен и обновить Authorize. Cookie браузер отправляет автоматически.

## Демосессия (этап 03)

По умолчанию включён профиль `demo`. `POST /api/v1/demo/session` входит в подготовленный аккаунт «Демо-представитель» / «Демо-пекарня». Тело запроса не требуется, аккаунт выбирает сервер. Вторая компания «Демо-мастерская» подготовлена для будущих проверок доступа; переключения пользователя через API нет.

Проверить из PowerShell при запущенном backend:

```powershell
$baseUrl = 'http://localhost:8080'
$csrf = Invoke-RestMethod "$baseUrl/api/v1/csrf" -SessionVariable cabinetSession
Invoke-RestMethod "$baseUrl/api/v1/demo/session" -Method Post -WebSession $cabinetSession -Headers @{'X-CSRF-TOKEN' = $csrf.token}
$csrf = Invoke-RestMethod "$baseUrl/api/v1/csrf" -WebSession $cabinetSession
Invoke-RestMethod "$baseUrl/api/v1/me" -WebSession $cabinetSession
```

Первый вход меняет ID сессии и сбрасывает CSRF. Повторный демовход с актуальным токеном сохраняет аккаунт и ID сессии. Контекст пользователя сохраняется в HTTP-сессии; после перезапуска backend нужно войти заново. `CurrentUserProvider` даёт остальным сервисам `userId` и `companyId` текущей сессии.

GET `/api/v1/me` без входа возвращает `401 SESSION_REQUIRED`; POST без правильного CSRF — `403 CSRF_INVALID`. Ошибки Security имеют тот же `ProblemDetail`, что ошибки контроллеров. Swagger и `/actuator/health` доступны без входа; остальные запросы защищены. Формы входа, Basic Auth и генерации стандартного пароля Spring нет.

Cookie `JSESSIONID`: `HttpOnly`, `Path=/`, `SameSite=Lax`; servlet-контейнер добавляет `Secure` для HTTPS. Локально используется HTTP. Фронтенд обращается к `/api` через Vite proxy на `localhost:8080`, отдельный CORS сейчас не настроен.

При явном выборе профиля без `demo` (например, `--spring.profiles.active=local`) демовход возвращает `404`. Демопрофили в БД остаются синтетическими данными миграции V2.

## Каталог продуктов (этап 04)

После демовхода: `Invoke-RestMethod "$baseUrl/api/v1/products" -WebSession $cabinetSession`. Ответ содержит `items` с кодом, названием, описанием и `terms`. Только активные продукты, порядок по коду, максимум 100 записей. Без входа — `401 SESSION_REQUIRED`.

Суммы, сроки, ставки и периоды соответствуют разделу 2 `docs/CREDIT_POLICY_AND_ML_REQUIREMENTS.md`. Суммы и проценты передаются строками с двумя знаками после точки. Правила овердрафта, возобновляемой линии и госконтракта заполнены только для соответствующего продукта; остальные объекты правил — `null`.

`CatalogService.findActiveProductTerms(code)` возвращает неизменяемые условия `ProductTerms` для будущих заявок и помощника; для отсутствующего или неактивного продукта — пустой `Optional`. Другим областям не требуется обращаться к репозиторию каталога. Версия условий хранится в `terms.version`; изменения условий оформляются новой миграцией и новой версией.

Каталог содержит демонстрационные условия. Расчёт доступного лимита для конкретной компании и проверки заявки появятся на следующих этапах; расчёта платежей и обслуживания траншей здесь нет.

## Идемпотентность команд (этап 05)

`common.idempotency.IdempotencyService` используется явно из сервисов заявок и чата. Новых HTTP-операций этот этап не добавляет. Область ключа задаётся `IdempotencyScope`: текущие `userId`, `companyId`, версионированная операция (например, `applications.create.v1`), ресурс (`collection` либо ID) и UUID из `Idempotency-Key`. Сессию, CSRF и `requestId` передавать в область или DTO для хеша не нужно.

Порядок вызовов:

1. Сервис сценария проверяет права пользователя на ресурс.
2. `begin(scope, requestDto, lease)` возвращает `Replay` с исходным успешным ответом либо `Claim` с ID записи и токеном выполнения. SHA-256 считается по JSON DTO: порядок свойств объектов и пробелы JSON не влияют, порядок массивов и строковые значения сохраняются.
3. Для `Replay` вернуть `response().toResponseEntity()` до проверки версии и текущего состояния ресурса.
4. Для `Claim` выполнить бизнес-действие и вызвать `complete(claim, status, responseDto, headers)` в той же транзакции, что запись бизнес-результата. Метод требует существующей транзакции; при потере токена или истечении срока бросает исключение, откатывающее её.

Короткая команда может вызвать `begin` и `complete` внутри своей общей `@Transactional`-операции. Для долгой генерации `begin` выполняется отдельной короткой транзакцией, вызов LLM — без транзакции, сохранение сообщений и `complete` — вместе в новой транзакции. Границы задаёт вызывающий сервис; длительность захвата должна покрывать его конечный таймаут и сохранение результата. Не удерживать транзакцию во время вызова модели.

При другом теле возвращается `409 IDEMPOTENCY_KEY_REUSED`, при активном выполнении — `409 OPERATION_IN_PROGRESS`. Два запроса с одинаковой областью сериализуются через уникальное ограничение и блокировку строки PostgreSQL. После технического сбоя `markRetryableFailure(claim)` разрешает повтор с тем же телом; вызывать после отката бизнес-транзакции либо без неё. Истёкший захват можно занять новым токеном. Старый токен не сохраняет успех и не сбрасывает новый захват.

Проверку единственной активной попытки рассмотрения или генерации выполняет соответствующий бизнес-сервис: новый ключ не должен обходить это ограничение.

Сохраняются только успешный статус `2xx`, JSON-объект ответа и значимые заголовки `Location`/`Content-Type`. Cookie, CSRF и старый `X-Request-Id` не сохраняются. При повторе фильтр добавляет новый ID запроса и `Cache-Control: no-store`. Ошибки генерации успешным ответом не считаются. Успех и запись о техническом сбое доступны для очистки через 24 часа; `deleteExpired` выполняется раз в час и никогда не удаляет `IN_PROGRESS`, даже с истёкшим захватом.

Одна целевая проверка механизма на уже запущенной локальной БД с миграциями V1–V3:

```powershell
.\mvnw.cmd '-Dtest=IdempotencyServiceTest' '-Didempotency.db-test=true' test
```

Проверка не запускает приложение, HTTP, LLM или Testcontainers. Использует демопользователя V2, создаёт только собственные записи `test.stage05.*` и удаляет их после выполнения. При обычной сборке эта проверка БД пропускается. Новых зависимостей и миграций для этапа нет.

## Черновики заявок (этап 06)

После входа доступны:

| Операция | Поведение |
|---|---|
| `POST /api/v1/applications` | Создать DRAFT по `productCode`; требуется UUID `Idempotency-Key` |
| `GET /api/v1/applications` | Страница заявок текущей компании; `page=0`, `size=20`, необязательный `status` |
| `GET /api/v1/applications/{applicationId}` | Восстановить карточку и форму |
| `PUT /api/v1/applications/{applicationId}/form` | Заменить форму с `expectedVersion`; без `Idempotency-Key` |

Компания и представитель берутся из сессии. Неизвестный/неактивный продукт при создании даёт `422 VALIDATION_FAILED`. Создание заявки, события `DRAFT` и сохранение успешного идемпотентного ответа проходят в одной транзакции. Повтор POST возвращает исходную карточку создания; актуальное состояние читается GET.

`calculationDate` — UTC-дата создания. Финансовый период — 3, 6 либо 12 полных месяцев перед месяцем создания согласно продукту. Дата и границы фиксируются в БД. У черновика нет рассмотрения, решения или технической ошибки; `requiredInformation=[]`. `allowedActions=[UPDATE_FORM,SUBMIT]` соответствует контракту DRAFT; submit реализован на этапе 10.

PUT принимает все девять ключей `form`, даже если значения `null`. Пропущенный ключ даёт `400 MALFORMED_REQUEST`; `null` очищает поле. Неполная применимая форма допустима. Неприменимые поля дают `422 VALIDATION_FAILED`: цель/бюджет только для LONG_TERM, срок транша только для REVOLVING_LINE, госконтракт только для GOVERNMENT_CONTRACT_LINE. Проверки готовности формы к submit и кредитные ограничения относятся к этапу 07.

Сохранение реализовано для DRAFT и запрошенного поля в NEEDS_INFO. В MVP уточняется только averageMonthlyInflow; остальные поля при таком PUT должны остаться прежними. Вопрос закрывается ответом через submit. Несовпадение версии даёт `409 VERSION_CONFLICT`, запрещённое состояние — `409 INVALID_APPLICATION_STATE`. Отклонённый запрос не изменяет форму. `@Version` также защищает от двух одновременно выполняющихся сохранений. Обычное сохранение формы не добавляет событие перехода состояния.

Чужая и отсутствующая заявка дают одинаковый `404 NOT_FOUND`. Список сортируется по `updatedAt DESC, id DESC`, размер страницы 1–100, страница за пределами списка пуста. Для списка выбираются только поля краткой карточки. `ApplicationService.getApplication(id)` предоставляет чтение с проверкой компании и для будущего помощника.

Пример после демовхода из раздела выше:

```powershell
$creationKey = [guid]::NewGuid().ToString()
$draft = Invoke-RestMethod "$baseUrl/api/v1/applications" -Method Post -WebSession $cabinetSession -ContentType 'application/json' -Headers @{'X-CSRF-TOKEN' = $csrf.token; 'Idempotency-Key' = $creationKey} -Body '{"productCode":"WORKING_CAPITAL"}'
$draft.form.amount = '500000.00'
$saveBody = @{expectedVersion = $draft.version; form = $draft.form} | ConvertTo-Json -Depth 8
$saved = Invoke-RestMethod "$baseUrl/api/v1/applications/$($draft.id)/form" -Method Put -WebSession $cabinetSession -ContentType 'application/json' -Headers @{'X-CSRF-TOKEN' = $csrf.token} -Body $saveBody
Invoke-RestMethod "$baseUrl/api/v1/applications/$($draft.id)" -WebSession $cabinetSession
Invoke-RestMethod "$baseUrl/api/v1/applications?page=0&size=20&status=DRAFT" -WebSession $cabinetSession
```

Целевая проверка на существующей локальной PostgreSQL с миграциями V1–V3:

```powershell
.\mvnw.cmd '-Dtest=ApplicationServiceTest' '-Dapplications.db-test=true' test
```

Проверяются реальные контроллеры и сервисы через MockMvc, запись в PostgreSQL, повтор создания, варианты пяти форм, очистка null, неизменность при ошибке/старой версии, изоляция компаний, порядок и пагинация, общий откат заявки/события/идемпотентности. Созданные проверкой данные удаляются после выполнения. LLM и скоринг не вызываются; Testcontainers и дополнительные скрипты не используются. При обычной сборке проверка БД пропускается.

## Правила рассмотрения (этап 07)

`credit.decision` содержит правила без обращения к БД, HTTP и моделям. SubmissionValidator подключён к submit на этапе 10; исполнение кредитной политики и внешние вызовы подключаются фоновым обработчиком на этапе 11. Сохранение неполного черновика продолжает работать по правилам этапа 06.

`SubmissionContext` передаёт форму, код и условия продукта, дату создания, закреплённый финансовый период и дату принятия попытки `asOfDate`. `SubmissionValidator.validate(context)` возвращает ошибки полей. При будущем submit непустой список означает `422`: рассмотрение не создаётся, состояние заявки не меняется. Проверяются обязательность, диапазоны суммы/срока, точность денег, применимость специальных полей, цель и положительный бюджет, срок транша, реквизиты/даты госконтракта и период. Условие «кредит не больше бюджета проекта» не вводится.

Овердрафт ограничен минимумом максимума продукта и 30% поступлений; госконтракт — минимумом максимума продукта и 70% от стоимости за вычетом аванса. Проценты берутся из переданных условий продукта. Вычисленный предел округляется вниз до копейки, введённая сумма не округляется. Даже подтверждённый ноль поступлений не позволяет отправить овердрафт с положительной суммой.

Финансовый период проверяется относительно `calculationDate`. Возраст бизнеса считается в полных месяцах между регистрацией и `asOfDate`. Плановое окончание — `asOfDate.plusMonths(termMonths)`, с календарными месяцами. Для госконтракта исполнение не раньше `asOfDate`; плановое окончание не раньше исполнения и не позже окончательной оплаты плюс допустимые 30 дней. Повторное рассмотрение/технический retry должны передавать даты согласно политике, правила сами не берут текущую дату.

Порядок вызовов сценария (приём реализован на этапе 10, исполнение — на этапе 11):

1. Проверить доступ, успешный идемпотентный повтор, версии/состояние и ошибки `SubmissionValidator`; принять попытку.
2. В обработчике вызвать `CreditDecisionPolicy.checkCompany`: возраст, требуемый счёт, регулярность. Метод возвращает первую причину отказа либо пустой результат.
3. Получить и проверить кредитный отчёт, затем вызвать `checkCurrentOverdueDebt`. При `AVAILABLE` нужна неотрицательная сумма; положительная просрочка даёт `CURRENT_OVERDUE_DEBT`. Для `NO_HISTORY` сумма должна быть `null`, автоматического отказа/одобрения нет. Получение и полная проверка отчёта относятся к этапу 08.
4. Вызвать `requiredInflowConfirmation`, передав принятые подтверждения только этой заявки. При нуле и отсутствии совпадения по полю, значению и всему финансовому периоду возвращается потребность `ZERO_INFLOW_CONFIRMATION`. ID вопроса, запись в БД и проверка ответов на него добавляются в сценарии уточнений.
5. Вызвать скоринг и передать `RiskEstimate` в `decideByRisk` вместе с закреплёнными `PolicyParameters` и временем решения. Некорректная версия модели/схемы, отсутствующий риск и любые значения кроме `0` и `1` вызывают `InvalidRiskEstimateException`; технический сбой не превращается в кредитный отказ.

`riskScore < riskCutoff` означает одобрение, равенство и превышение — отказ `RISK_THRESHOLD_EXCEEDED`. Сравнение `BigDecimal` без предварительного округления. Схема 4 использует бинарный результат 0/1 и фиксированный порог 0.50 из ml/scoring/policy.json. Версия алгоритма закреплена в scoring.expected-model-version; поля modelVersion/riskScore сохранены для совместимости.

`CreditDecision`, `DecisionReason` и `ApprovedTerms` находятся в `credit.model` и используются также DTO карточки. ## Кредитная история (этап 08)

`CreditHistoryProvider.getCreditHistory(companyId)` возвращает типизированный `CreditHistoryReport` либо `CreditHistoryException`. Реализация `DemoCreditHistoryProvider` читает JSON из `src/main/resources/demo/credit-history/{companyId}.json`. Компания будущего вызова берётся из сохранённой заявки после проверки доступа. Новых endpoint'ов и таблиц нет; получение ещё не подключено к обработчику рассмотрения.

Каждый вызов провайдера создаёт новый отчёт; при техническом retry обработчик должен использовать прежний сохранённый отчёт, если он уже был получен. ## Отправка и технический повтор (этап 10)

POST /api/v1/applications/{applicationId}/submit принимает expectedVersion, expectedProductTermsVersion и необязательный clarificationResponses (по умолчанию []). Форма должна быть предварительно сохранена через PUT; submit использует данные БД. Обязательны сессия, CSRF и UUID Idempotency-Key. Разрешённые состояния — DRAFT и NEEDS_INFO.

Порядок: доступ компании → поиск идемпотентного повтора → блокировка заявки → состояние/версия → активный продукт под разделяемой блокировкой → версия условий → проверка полной формы и уточнений → запись. Блокировка каталога удерживается до commit: обновление продукта не может попасть между чтением версии и копированием условий. Независимые отправки одной заявки дают одну попытку; второй submit получает 409 APPLICATION_ALREADY_SUBMITTED. Некорректная форма — 422 VALIDATION_FAILED, версия — 409 VERSION_CONFLICT, условия — 409 PRODUCT_TERMS_CHANGED с currentProductTermsVersion.

AssessmentInput — внутренний тип снимка schemaVersion=2: продукт с условиями, форма с cashBalance, расчётная дата/финансовый период, asOfDate принятия, необходимые сведения компании и применимые подтверждения. Кредитный отчёт хранится отдельно. Параметры политики, схема признаков 4, ожидаемая версия Python и порог закреплены в попытке. JSONB читает и пишет Hibernate через тот же JsonMapper, что и API, чтобы денежный формат и даты не расходились.

Одна транзакция сохраняет credit_assessment с processing_status=READY, текущую попытку, CHECKING/версию/время заявки, событие и успешный ответ идемпотентности. Очередь — строки credit_assessment; новых таблиц или миграций нет. Ответ — 202 ProcessingAccepted с applicationId, assessmentId, version, acceptedAt, statusUrl и pollAfterSeconds=2; Location указывает на GET карточки. Повтор исходного ключа возвращает тот же 202 даже после завершения рассмотрения. Актуальное состояние читается GET. Чтение карточки выполняется в короткой read-only транзакции REPEATABLE_READ, чтобы состояние заявки и её текущая попытка читались согласованно.

В NEEDS_INFO обязательны ответы ровно на текущие вопросы. CONFIRM_VALUE подтверждает сохранённый 0.00 и записывает подтверждение поля/значения/периода в снимок. VALUE_CORRECTED требует сначала сохранить положительные поступления через PUT. Пропуск ответа — 422 CLARIFICATION_RESPONSE_REQUIRED; дубликат/противоречие — 422 CLARIFICATION_RESPONSE_CONFLICT; ответ в DRAFT — 422 CLARIFICATION_NOT_EXPECTED; чужой или устаревший вопрос — 409 CLARIFICATION_STALE. Ответы и новая попытка фиксируются одной транзакцией. Новая отправка после уточнения получает новый asOfDate и ещё не содержит кредитного отчёта.

POST /api/v1/applications/{applicationId}/retry принимает только expectedVersion, требует тот же набор заголовков и доступен из TECHNICAL_HOLD. Новая попытка получает следующий номер и ссылку на прежнюю. Копируются input_snapshot, подтверждения, исходные даты, все параметры политики и уже полученный credit_history_snapshot. Если отчёта не было, сохраняется null. Текущий каталог и новая конфигурация политики старые условия не заменяют.

GET показывает текущий продукт для DRAFT/NEEDS_INFO; для CHECKING/TECHNICAL_HOLD/APPROVED/DECLINED — сохранённый продукт попытки. В CHECKING allowedActions пуст, в TECHNICAL_HOLD доступен RETRY, в NEEDS_INFO — UPDATE_FORM/SUBMIT. Формат ApplicationView сохранён.

На этапе 10 попытки только принимались; после подключения 11.2–11.3 READY обрабатываются автоматически. Вызовы кредитного источника/Python и автоматическое исполнение подключаются на этапе 11. Для проверки текущих переходов NEEDS_INFO/TECHNICAL_HOLD тест сам готовит завершённую предыдущую попытку; это не рабочая реализация обработчика.

## Получение попытки на обработку (этап 11.1)

AssessmentClaimService.claimNext() получает одну доступную READY-попытку. Метод выполняется в отдельной короткой транзакции REQUIRES_NEW; репозиторий использует только JdbcTemplate. Возвращается Optional<AssessmentClaim>: ID попытки/заявки, UUID token, lockedUntil и executionCount. Пустой Optional означает, что свободной доступной попытки сейчас нет.

Один SQL-запрос выбирает строку по next_run_at/id с FOR UPDATE SKIP LOCKED, переводит её в RUNNING, назначает новый токен, срок и увеличивает execution_count. next_run_at сравнивается со временем PostgreSQL; срок захвата тоже задаёт БД. Будущие и уже RUNNING-попытки не выбираются. Настройка credit.processing.lease-duration=30s находится в application.yaml. attempt_no при захвате не меняется: это запуск существующей попытки, а не новый submit/retry.

Блокировка строки и соединение транзакции освобождаются до возврата claimNext(). Срок 30 секунд — сохранённое право обработки с токеном, а не удержание SQL-блокировки или соединения на 30 секунд. JDBC-захват не загружает управляемую CreditAssessment; дальнейшая работа со снимком должна открывать новую короткую транзакцию и новый persistence context. Ранее загруженную JPA-сущность между захватом и сохранением результата переиспользовать нельзя.

AssessmentClaimRepository.lockOwned(claim) разрешён только внутри существующей транзакции. Он блокирует строку текущего владельца и проверяет срок захвата после получения блокировки. Для этого используется материализованный CTE: проверка времени выполняется после ожидания блокировки. Чужой/старый токен, другая заявка, завершённая попытка или истёкший срок дают пустой результат. Метод не заменяет проверку токена/срока и актуальной попытки при финальной записи на этапе 11.2.

На этапе 11.1 подготовлен метод захвата без нового HTTP endpoint; автоматический запуск добавлен в 11.2. В обычном пользовательском потоке submit пока оставляет READY/CHECKING. Scheduler и исполнение подключаются на 11.2, восстановление истёкших RUNNING — на 11.3. Статус заявки при захвате остаётся CHECKING. Spring AI относится к помощнику, а не к получению задания.

Целевая проверка из backend/:

```powershell
.\mvnw.cmd '-Dtest=AssessmentClaimServiceTest' '-Dapplications.db-test=true' test
```

Пять проверок выполняются на PostgreSQL в отдельной случайно названной схеме. Таблица очереди копирует столбцы, проверки и индексы public.credit_assessment; внешние ключи к пользовательским данным не копируются. Проверяются порядок/отложенные задания, пропуск заблокированной строки, освобождение блокировки до возврата, конкуренция за одну попытку, токен/срок и откат захвата. После выполнения временная схема удаляется. Spring Boot, Flyway, Python и LLM для этого набора не запускаются; очередь public не изменяется.

## Исполнение и восстановление (этапы 11.2–11.3)

AssessmentWorker включён по умолчанию (credit.processing.enabled=true). Один цикл восстанавливает одну просроченную попытку, затем получает и исполняет одну READY. Циклы последовательные, пауза после завершения — credit.processing.poll-delay=1s. Spring AI здесь не участвует: расчёт выполняется отдельным Python через существующий HTTP-клиент. Для ручных тестов/отладки worker можно отключить свойством credit.processing.enabled=false.

ProcessApplicationService.process(claim) запрещает внешнюю транзакцию через Propagation.NEVER. Он связывает готовые правила: данные сохранённой попытки → возраст/счёт/регулярность → кредитный отчёт → текущая просрочка → подтверждение нуля → скоринг схемы 4 → решение. Ранний отказ не обращается к внешним компонентам. NO_HISTORY передаётся в Python с четырьмя null; текущая просрочка отказывает до уточнения нуля. После ответа на уточнение новая попытка проходит этот же сценарий.

CreditHistoryService ограничивает всё получение и валидацию отчёта бюджетом credit.processing.credit-history-timeout=5s. Provider запускается через отдельный executor виртуальных потоков; по таймауту ожидание прекращается и задача отменяется. Полный отчёт проверяется на принадлежность компании, формат и дату относительно asOfDate попытки. Отчёт сохраняется один раз в отдельной короткой транзакции до вызова Python. При восстановлении или техническом retry сохранённый отчёт повторно используется; новый отчёт его не заменяет. Демоисточник по-прежнему читает JSON, реального БКИ нет.

AssessmentStateService открывает отдельные короткие транзакции для чтения, записи отчёта и завершения. Во всех случаях сначала блокируется заявка, затем проверяется текущая попытка и захват. JPA-сущность попытки после чтения отсоединяется, наружу возвращается AssessmentWork с неизменяемыми данными. Запись отчёта и завершение выполняются условным SQL по ID/токену/RUNNING/сроку БД. Отчёт сохраняется через COALESCE, поэтому уже записанный документ остаётся прежним. Ожидание кредитного источника и Python выполняется без соединения бизнес-транзакции.

Завершение атомарно записывает результат FINISHED/outcome, risk_score/actual_model_version при наличии расчёта, результат JSONB, время и очистку захвата; изменяет статус/версию заявки; создаёт вопрос при NEEDS_INFO и событие перехода. Перед финальной записью заново проверяется срок PostgreSQL. Потеря захвата откатывает изменения заявки и вопроса. Старый или уже завершённый запуск не может перезаписать результат. Для Python используется requestId принятия попытки, найденный в событии CHECKING.

Четыре исхода: APPROVED/DECLINED с CreditDecision; NEEDS_INFO с сохранённым вопросом ZERO_INFLOW_CONFIRMATION; TECHNICAL_HOLD с CREDIT_HISTORY_*, SCORING_* либо PROCESSING_INTERRUPTED. Ошибка источника останавливает вызов Python; технические ошибки не превращаются в кредитный отказ. Число и версия алгоритма проверяются относительно закреплённой политики, а не подменяются текущей конфигурацией.

AssessmentRecoveryService выбирает просроченный RUNNING с блокировкой заявки и SKIP LOCKED, затем блокирует попытку. Порядок блокировок совпадает с завершением и submit/retry. До credit.processing.max-executions=3 попытка возвращается в READY с credit.processing.retry-delay=1s; номер попытки, снимки и политика сохраняются. Новый захват назначает новый токен и увеличивает execution_count. После лимита попытка завершается TECHNICAL_HOLD/PROCESSING_INTERRUPTED, в карточке доступен RETRY. Пользовательский retry создаёт новую попытку, сохраняя исходные данные и уже полученный отчёт.

Срок захвата по умолчанию 30s. При старте проверяется, что он больше суммы бюджета кредитной истории, бюджета HTTP-скоринга и запаса 5s. Продления захвата и бесконечных повторов нет. При перезапуске приложения очередь читается из БД; ещё действующий RUNNING ожидает истечения срока, просроченный восстанавливается очередным циклом.

Целевая проверка из backend/:

```powershell
.\mvnw.cmd '-Dtest=ProcessingPipelineTest,AssessmentClaimServiceTest' '-Dapplications.db-test=true' test
```

ProcessingPipelineTest создаёт отдельную случайную схему и применяет в неё V1–V4 с seed-данными, затем удаляет схему. Существующие заявки/очередь public не изменяются. Управляемые адаптеры существуют только в тесте для ошибок, таймаута и задержанных ответов. Проверяются пять продуктов, ранние отказы, NO_HISTORY, уточнения, сохранение отчёта, восстановление, лимит запусков и запоздалые источники/расчёты. Для прогона того же обработчика с настоящим Python дополнительно передать -Dprocessing.real-scoring=true и -Dscoring.base-url=http://127.0.0.1:8000. Без флага реальный внешний тест пропускается.

## Диалоги и история помощника (этап 12)

Реализованы POST /api/v1/assistant/conversations, GET /api/v1/assistant/conversations/{id}/messages и POST /api/v1/assistant/conversations/{id}/messages. Все требуют сессию; POST дополнительно CSRF и UUID Idempotency-Key. Создание без тела возвращает ConversationView/201 и Location на историю. История поддерживает afterSequence=0, limit=50 (максимум 100), выдаёт sequence по возрастанию и hasMore; пустая страница сохраняет переданный afterSequence в lastSequence. Диалог принадлежит пользователю и компании одновременно; чужой диалог — 404.

SendMessageRequest содержит text (непустой, максимум 2000 символов) и context с тремя обязательными nullable-ключами applicationId/productCode/fieldCode. Без заявки диалог работает с application=null. Доступ к выбранной заявке проверяется до поиска успешного повтора команды и перед финальной записью. Несовпадение продукта и заявки, недоступный продукт, неизвестное или неприменимое поле — 422 до gateway.

AssistantContext v2 и AssistantReply v1 соответствуют общим JSON Schema и копии ML-команды. Каталог формируется из ProductTerms БД; для выбранной отправленной заявки её продукт получает закреплённые условия из снимка, соответствующие карточке. История — последние 20 сообщений полными парами. Набор fieldDefinitions хранится в src/main/resources/assistant/field-definitions.json и содержит реальные пути формы, периоды 3/6/12 и cashBalance. Старый ml/llm/fields.json описывает отдельный синтетический стенд и не используется как нормативный источник полей.

В application.fieldValues передаются только выбранное поле и нужные зависимости; без текущего поля — сумма/срок. Полный кредитный отчёт, банковские признаки и номер госконтракта из формы не передаются. Для вопроса о номере достаточно определения поля. Контекст и историю собирает сервер; браузер не может передать собственный каталог или чужую историю.

AssistantService.send запрещает внешнюю транзакцию через Propagation.NEVER. Первая короткая транзакция AssistantStateService.prepare проверяет доступ, резервирует идемпотентную команду и диалог, затем собирает контекст. После commit gateway вызывается через отдельный executor без транзакции БД. Бюджет assistant.timeout=60s, захваты команды и диалога assistant.lease-duration=75s. Проверка конфигурации требует запас больше 5 секунд относительно бюджета.

После корректного ответа вторая короткая транзакция сначала блокирует действующий токен команды, затем диалог. Создаёт USER и ASSISTANT, условно увеличивает next_sequence на 2 и освобождает токен диалога, сохраняет исходный HTTP-ответ в идемпотентности. Проверяются срок PostgreSQL и оба токена. При потере захвата откатываются оба сообщения и счётчик. Порядок блокировок команды → диалога одинаков при резервировании, завершении и очистке после сбоя; native UPDATE очищают persistence context после flush, чтобы старый JPA-объект не затёр новые значения.

Повтор успешного ключа возвращает исходный MessageExchange/200 без gateway и новых сообщений. Другой запрос в занятом диалоге — 409 CONVERSATION_BUSY, повтор ещё выполняемой команды — 409 OPERATION_IN_PROGRESS. Ошибка не добавляет ни вопрос, ни ответ: команда переводится в RETRYABLE_FAILURE, захват диалога освобождается условно по своему токену. Тот же ключ можно повторить, контекст собирается заново. После аварии истёкшие захваты заменяются при следующей отправке; поздний запуск не может записать ответ или освободить чужой захват.

AssistantReplyValidator проверяет ответ, его длину/HTML, принадлежность рекомендуемого кода входному каталогу и технические метаданные. Ответ хранится как text, а внутренний generation_metadata содержит версии схем, модель/digest/промпт/параметры и идентификаторы разрешённого контекста, без полной анкеты. В HTTP ChatMessage метаданные не выдаются. Строгий разбор сырого JSON и проверка фактов выполняются подключённым LLM-адаптером.

AssistantConfig подключает OllamaAssistantGateway. Без доступной закреплённой модели отправка возвращает 503 ASSISTANT_UNAVAILABLE; некорректный ответ даёт 502 ASSISTANT_INVALID_RESPONSE, превышение бюджета — 504 ASSISTANT_TIMEOUT. Во всех случаях новая пара сообщений не сохраняется.

Целевая проверка из backend/:

```powershell
.\mvnw.cmd '-Dtest=AssistantServiceTest' '-Dapplications.db-test=true' test
```

Набор использует отдельную временную схему PostgreSQL с V1–V4; существующие данные не изменяются. Контролируемый gateway доступен только в тесте и не попадает в рабочий JAR. Проверяются права, контекст, пагинация/20 сообщений, идемпотентность, busy, ошибки/повтор, таймаут и запоздалые ответы при смене каждого токена. Новых миграций, зависимостей или отдельного Python-сервера помощника нет.
