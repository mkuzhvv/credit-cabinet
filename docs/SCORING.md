# Формальный скоринг

[ml/scoring](../ml/scoring/) — внутренний Python HTTP-сервис проверки платёжеспособности. Он работает без LLM и GPU. В общем приложении запускается контейнером `scoring`; Java обращается к `http://scoring:8000`.

Алгоритм детерминированный. Обученные веса, обучение на кредитных исходах и оценка вероятности дефолта в текущем контуре не используются.

## 1. Исходники и параметры

| Файл | Назначение |
|---|---|
| [server.py](../ml/scoring/server.py) | HTTP-сервер и маршруты здоровья/расчёта |
| [engine.py](../ml/scoring/engine.py) | Денежная модель и версия алгоритма |
| [validation.py](../ml/scoring/validation.py) | Проверка входа и согласованности признаков |
| [schema.json](../ml/scoring/schema.json) | JSON Schema признаков версии 4 |
| [policy.json](../ml/scoring/policy.json) | Стресс, коэффициенты и порог |
| [catalog.json](../ml/scoring/catalog.json) | Условия продуктов, используемые расчётом |
| [requirements.txt](../ml/scoring/requirements.txt) | Зафиксированные Python-зависимости |

Правила, схема и каталог загружаются при старте. Для альтернативных файлов предусмотрены параметры `--policy`, `--catalog` и переменные `SCORING_POLICY_PATH`, `SCORING_CATALOG_PATH`. Базовый Compose использует файлы образа.

Каталог Python — отдельный артефакт расчёта. Его условия должны совпадать с серверными продуктами; изменение требует проверки и обновления связки версий.

## 2. HTTP

Полная спецификация: [Scoring OpenAPI 0.4.0](contracts/scoring.openapi.yaml).

| Метод и путь | Назначение |
|---|---|
| `GET /health/live` | Процесс отвечает: `{"status":"UP"}` |
| `GET /health/ready` | Готовность правил, версия схемы, алгоритма и список продуктов |
| `POST /internal/v1/assessments` | Проверка признаков конкретной попытки |

Запрос содержит `assessmentId`, `applicationId`, `featureSchemaVersion="4"` и `features`: продукт, сумму, срок, финансы, cashBalance, даты, возраст бизнеса, кредитный профиль и применимые параметры продукта.

Java формирует признаки из сохранённых снимков. Пользователь, номер контракта, текст цели, cookie и CSRF не передаются. Python не читает PostgreSQL и не получает сведения о компании из внешнего источника.

Успех возвращает assessmentId, featureSchemaVersion, modelVersion и riskScore. Значение риска строго 0 или 1.

## 3. Денежная модель

```text
F = 0.90 × averageMonthlyInflow − averageMonthlyOutflow
C₀ = cashBalance
Cₜ = Cₜ₋₁ + F − 1.30 × новый платёжₜ
Успех: min(C₀, …, Cₕ) ≥ averageMonthlyOutflow
```

- Поступления уменьшаются на 10%.
- Платёж по новому финансированию увеличивается коэффициентом 1,30.
- Требуется резерв в один месяц расходов, включая начальный момент.
- Новый кредит не прибавляется к собственным деньгам.
- Существующие кредитные платежи уже учтены в расходах и повторно не вычитаются.
- Равенство резерву допускается.

Расчёты используют Decimal. Платежи округляются вверх до копейки; остатки при сравнении не округляются.

| Продукт | Расчётный сценарий |
|---|---|
| WORKING_CAPITAL / LONG_TERM | Аннуитет по годовой ставке продукта |
| OVERDRAFT | Полная выборка и погашение с процентами за 30/365 в каждом месяце лимита |
| REVOLVING_LINE | Последовательные полные транши; равные доли основного долга и проценты на остаток |
| GOVERNMENT_CONTRACT_LINE | Ежемесячные проценты, основной долг в конце срока |

Это консервативные сценарии демонстрационного расчёта. Приложение не ведёт фактические выдачи, транши и банковское обслуживание.

## 4. Версии и интеграция Java

Закреплённая версия — `rules-cashflow-v1-59fdb57552ca`; схема признаков — `4`; порог — `0.50`.

Fingerprint зависит от кода алгоритма/валидации, схемы, каталога и политики. Неожиданная версия не принимается автоматически. После согласованного изменения обновляется и `scoring.expected-model-version` Java.

[HttpRiskScoringClient](../backend/src/main/java/com/creditcabinet/credit/scoring/HttpRiskScoringClient.java) сначала проверяет `/health/ready`, затем вызывает расчёт. Общий бюджет — 10 секунд, подключение — до 2 секунд. Повтор HTTP внутри адаптера автоматически не выполняется.

Клиент проверяет ID, схему, точную версию, JSON и бинарный результат. Ошибки `SCORING_UNAVAILABLE`, `SCORING_TIMEOUT`, `SCORING_INVALID_RESPONSE` переводят попытку в `TECHNICAL_HOLD`; они не считаются отказом по риску.

Результат 0 при выполненных бизнес-правилах позволяет одобрение. Результат 1 даёт `DECLINED / RISK_THRESHOLD_EXCEEDED`. Обязательные проверки Java выполняются раньше; текущая просрочка может завершить заявку без Python.

## 5. Проверка и ограничения

В контейнерном запуске readiness проверяется healthcheck. Логи:

```bash
docker compose logs --tail 100 scoring
```

Полный сценарий — в [демонстрации](BACKEND_SCENARIOS.md). Изменение алгоритма требует сверки контрактов и результатов для всех пяти продуктов.

Алгоритм не моделирует сезонность, внутримесячные разрывы, дополнительную будущую выручку или статистическую вероятность невозврата. `NO_HISTORY` не заменяет неизвестные показатели нулями; сведения истории сохраняются как отдельные признаки. Формальное одобрение не является банковским решением.
