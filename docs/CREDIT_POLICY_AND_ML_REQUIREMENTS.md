# Кредитная политика MVP и требования к ML-скорингу

Договорённости от 23.10.2026. Документ фиксирует правила решения, демонстрационные условия продуктов, требования к модели и результаты, которые передаёт ML-команда.

Форматы HTTP-запросов и ответов определяются [Scoring OpenAPI](contracts/scoring.openapi.yaml) и [Backend OpenAPI](contracts/backend.openapi.yaml). Настоящий документ дополняет [архитектуру](BACKEND_ARCHITECTURE.md) и [сценарии](BACKEND_SCENARIOS.md). Параметры демопродуктов заданы ниже; числа в примерах API остаются синтетическими примерами формата.

## 1. Принятые решения

| Область | Решение для MVP |
|---|---|
| Принятие решения | Правила продукта в Java + оценка ML + один порог риска |
| Модель | Начальный вариант — общая модель и общий порог для двух продуктов; пригодность данных для обоих продуктов подтверждает ML-команда |
| Направление оценки | `riskScore` от 0 до 1; больше означает больший риск |
| Граница порога | `riskScore < riskCutoff` — одобрение; `riskScore >= riskCutoff` — отказ, если остальные обязательные правила пройдены |
| Условия одобрения | Запрошенные сумма и срок, фиксированная ставка выбранного продукта |
| Настройка порога | ML подбирает и обосновывает порог до подключения версии модели; Java хранит его в кредитной политике |
| Критерий выбора | Минимум условного штрафа: 10 за одобренный проблемный кредит, 1 за отказ надёжному заёмщику |
| Дополнительное рассмотрение | Ручного рассмотрения и промежуточной зоны риска в MVP нет |
| Уточнение данных | `NEEDS_INFO` входит в MVP: подтверждение либо исправление нулевых поступлений до вызова ML |
| Кредитный профиль | Java получает синтетический отчёт через `CreditHistoryProvider`; в ML обязательны показатели и статус `AVAILABLE` или `NO_HISTORY` по схеме признаков `2` |
| LLM | Объясняет продукты и поля; не определяет риск, порог, ставку или кредитное решение. Отдельный [контракт LLM](contracts/llm/README.md) сохраняется |

Политика демонстрационная: реальную выдачу денег MVP не выполняет. Соотношение штрафов `10:1` — допущение проекта, а не оценка денежных потерь банка.

## 2. Демонстрационные условия продуктов

| Параметр | Оборотный кредит | Кредит на оборудование |
|---|---|---|
| Код | `WORKING_CAPITAL` | `EQUIPMENT` |
| Сумма | 100 000–5 000 000 ₽ | 100 000–10 000 000 ₽ |
| Срок | 6–24 месяца | 12–60 месяцев |
| Годовая ставка | 20% | 18% |
| Минимальный возраст бизнеса | 12 месяцев | 12 месяцев |
| Дополнительные сведения | Не требуются сведения об оборудовании | Название и положительная стоимость оборудования |
| Ограничение суммы покупки | — | Сумма кредита не превышает стоимость оборудования |

Эти значения — настройки демопродуктов, не действующие тарифы Альфа-Банка. Динамическая ставка по риску и автоматические альтернативные предложения в MVP не входят.

Финансовые показатели относятся к 12 полным календарным месяцам перед месяцем создания черновика. Для демонстрации нужен профиль компании с историей за весь период. Возраст компании в 12 месяцев сам по себе не подтверждает наличие такой истории.

## 3. Порядок рассмотрения

1. **Проверка формы до отправки.** Java проверяет обязательность, формат, сумму, срок, сведения об оборудовании и согласованность значений с продуктом. Исправимые ошибки возвращаются по полям; рассмотрение и скоринг не запускаются.
2. **Создание рассмотрения.** Java сохраняет снимок данных и условий, попытку, состояние `CHECKING` и фоновое задание в одной транзакции.
3. **Обязательные кредитные правила.** Например, несоответствие минимальному возрасту бизнеса приводит к отказу с фактической причиной `BUSINESS_TOO_YOUNG`. Если решение принято до скоринга, отсутствующая оценка остаётся `null`.
4. **Уточнение нулевых поступлений.** Если среднемесячные поступления равны `0.00` и для этого значения и отчётного периода нет принятого подтверждения, Java завершает попытку в `NEEDS_INFO` до вызова ML.
5. **Получение кредитного профиля.** Если предыдущие правила не завершили рассмотрение, Java получает отчёт через `CreditHistoryProvider` вне транзакции, проверяет компанию, показатели и даты. Под действующим захватом однократно сохраняет `credit_history_snapshot`. Уже полученный отчёт используется повторно. Недоступность, таймаут или неверный отчёт дают `TECHNICAL_HOLD` до ML.
6. **Вызов ML.** Java объединяет исходные признаки из `input_snapshot` и профиль из `credit_history_snapshot.profile` по схеме `2`; проверяет ответ, идентификатор попытки, версию схемы и ожидаемую версию модели.
7. **Применение порога.** При пройденных обязательных правилах риск ниже порога приводит к `APPROVED`, риск на пороге или выше — к `DECLINED` с причиной `RISK_THRESHOLD_EXCEEDED`.
8. **Сохранение результата.** Фиксируются данные, кредитный отчёт с метаданными источника, условия, вопросы и ответы пользователя, оценка при её наличии, версия модели, версия политики, порог, причины и история перехода.

Причина отказа соответствует сработавшему правилу. Отказ по порогу не подменяется объяснением про конкретный доход или расход, если такая причина отдельно не установлена.

Недоступность модели, таймаут или некорректный ответ приводят к `TECHNICAL_HOLD`. Техническая ошибка не заменяется оценкой риска, одобрением или кредитным отказом.

Кредитный профиль определён в [отдельном документе](CREDIT_HISTORY.md). `AVAILABLE` не означает положительную историю; `NO_HISTORY` означает успешную проверку без кредитных записей, а не сбой источника. При `NO_HISTORY` четыре показателя равны `null`, ML использует отдельное кодирование. Нового автоматического отказа по отсутствию истории или наличию просрочек нет: учитываются фактические признаки и порог риска.

`monthlyDebtPayment` не прибавляется повторно к `averageMonthlyOutflow`: существующие обязательства уже входят в расходы. Время состояния обязательств и период просрочек закрепляются отдельно от финансового периода формы. Технический `retry` сохраняет ранее полученный отчёт, а если получить его ещё не удалось — повторяет получение.

### Состояние NEEDS_INFO

В MVP включено правило `ZERO_INFLOW_CONFIRMATION` для обоих продуктов. После прохождения обязательных кредитных правил Java запрашивает подтверждение `form.averageMonthlyInflow = "0.00"`. Это правило демонстрационной политики, не установленное требование банка. Нулевое значение допустимо по формату и само по себе не является отказом.

Вопрос содержит `clarificationId`, код правила, поле, исходное значение и понятный текст. Пользователь выбирает один из двух путей:

| Ответ | Действия | Продолжение |
|---|---|---|
| `CONFIRM_VALUE` | Подтвердить, что нулевые поступления за указанный период верны; комментарий необязателен | Значение остаётся нулевым и передаётся в скоринг |
| `VALUE_CORRECTED` | Исправить поступления через сохранение формы, затем ответить на уточнение | Новая попытка использует исправленное положительное значение |

Ответ передаётся в `clarificationResponses` существующего `POST /applications/{applicationId}/submit` вместе с версиями заявки и условий. Отдельный endpoint и изменение Scoring API не нужны. Примеры и ошибки описаны в [руководстве по контрактам](contracts/README.md#уточнение-нулевых-поступлений).

Правила обработки:

- Во время `NEEDS_INFO` изменяется только запрошенное поле; сохранение формы не завершает уточнение и не запускает проверку.
- `submit` требует ответы на все текущие вопросы. Устаревшие или посторонние идентификаторы отклоняются.
- `CONFIRM_VALUE` принимается, только если сохранённое значение всё ещё совпадает с запрошенным `0.00`. `VALUE_CORRECTED` требует сохранённого положительного значения. Комментарий не заменяет подтверждение или исправление.
- Ответ, его связь с вопросом, новая попытка и задание сохраняются атомарно. Предыдущая попытка и её снимок остаются в истории.
- Подтверждение действует для конкретного поля, значения и отчётного периода. Следующая попытка и её технические повторы не запрашивают то же подтверждение заново; изменение значения делает прежнее подтверждение неприменимым.
- Сохраняются исходный вопрос и попытка, значение и период, тип ответа, комментарий при наличии, автор и время ответа, а также новая попытка. Подтверждение пользователя не означает внешнюю проверку данных.
- ML получает обычные числовые признаки, включая подтверждённый ноль. Ответ и комментарий пользователя не добавляются в признаки; LLM не разрешает уточнение.
- Подтверждение не гарантирует одобрение. Для нулевого значения возможен отказ по модели; корректность обработки нулевых поступлений проверяет ML-команда.

Промежуточный риск и ошибка Python не являются основаниями для `NEEDS_INFO`. Незаполненные обязательные поля выявляются до запуска рассмотрения.

## 4. Требования к данным и модели

ML-команда фиксирует в паспорте модели:

- Источник, версию и условия использования датасета; реальные или синтетические данные.
- Целевой исход, период его наблюдения и точное значение положительного класса `1`.
- Объём данных и количество проблемных и надёжных наблюдений в каждой выборке.
- Соответствие признаков обучения полям API, используемые преобразования и обработку пропусков.
- Использование кредитного профиля схемы `2`: суммы задолженности, платежей и просрочек, период и максимальные дни просрочки, отдельное кодирование `NO_HISTORY`. Принятие полей HTTP без использования моделью не считается поддержкой.
- Наличие данных по бизнес-кредитам и основания применять модель к каждому из двух продуктов.
- Ограничения модели и статус калибровки её оценки.

Метка «банк отказал» не равна метке «заёмщик не вернул кредит». Если исходные данные описывают только решение банка, это другая задача; её нельзя представлять как проверенный прогноз невозврата.

Модель использует только сведения, доступные на момент подачи заявки. Будущие просрочки и результаты погашения могут определять целевую метку, но не входные признаки.

Python выполняет preprocessing, не читает БД Java и не запрашивает дополнительные сведения у фронтенда. Нехватка признаков для выбранной модели обсуждается до интеграции; изменения согласуются в OpenAPI.

Без проверки калибровки `riskScore` называется оценкой риска. Значение `0.2` не объявляется вероятностью невозврата 20%.

## 5. Подбор и проверка порога

### Разделение данных

- **Обучающая выборка:** обучение модели и преобразований признаков.
- **Валидационная выборка:** сравнение и выбор порога.
- **Тестовая выборка:** итоговая проверка уже выбранной модели и порога; подстройка по её результату не выполняется.

Способ и размеры разделения описываются в отчёте. При наличии временной структуры и повторных наблюдений заёмщиков разделение учитывает их, чтобы исключить утечку будущих или связанных данных. Фильтрация по условиям продуктов и состав оцениваемой группы также описываются.

### Критерий выбора

Для каждого кандидата применяется то же правило границы, что и в Java:

```text
riskScore < threshold  → одобрение
riskScore >= threshold → отказ

weightedError = 10 × badApproved + goodDeclined
```

- `badApproved` — число одобренных наблюдений с проблемным исходом.
- `goodDeclined` — число отклонённых наблюдений с надёжным исходом.
- Выбирается минимальный `weightedError` на одной и той же валидационной выборке.
- При равном штрафе предпочтителен вариант с меньшим `badApproved`.
- Результат сравнивается со стратегиями «одобрять всем» и «отказывать всем» на той же группе данных.

Штраф в абсолютных числах нельзя напрямую сравнивать между выборками разного размера. Для такого сравнения дополнительно используется `weightedError / sampleCount`.

### Состав таблицы порогов

| Поле | Значение |
|---|---|
| `threshold` | Порог риска |
| `sampleCount` | Число наблюдений |
| `approvedCount` | Число одобрений |
| `approvalRate` | `approvedCount / sampleCount` |
| `badApproved` | Одобренные проблемные наблюдения |
| `goodDeclined` | Отклонённые надёжные наблюдения |
| `badRateAmongApproved` | `badApproved / approvedCount`; при отсутствии одобрений — `null` |
| `weightedError` | Условный штраф по формуле выше |
| `weightedErrorPerSample` | Штраф на одно наблюдение |

Итоговый тестовый отчёт содержит те же показатели для выбранного порога. ROC-AUC и PR-AUC дополняют оценку модели, но не заменяют критерий выбора порога. При наличии достаточных данных показатели дополнительно рассчитываются отдельно по продуктам.

Если модель не даёт преимущества перед простыми стратегиями по выбранному критерию, это фиксируется в отчёте. Проверка на синтетике не подтверждает качество на реальных бизнес-кредитах. Численные результаты не заполняются предположениями.

## 6. Результаты работы ML-команды

| Результат | Обязательное содержимое |
|---|---|
| HTTP-сервис | Реализация Scoring OpenAPI; поддержка обоих продуктов; корректные ошибки и проверки готовности |
| Артефакт модели и запуск | Версия модели и preprocessing, способ получения, зависимости, команды запуска и прогрева, требования к оборудованию |
| `MODEL_CARD.md` | Данные, целевой исход, признаки, разделение выборок, применимость, калибровка и ограничения |

| `evaluation.json` | Версии модели и схемы, выбранный порог, веса штрафа `10:1`, сведения о датасете и разделении, показатели на валидации и итоговом тесте, сравнение с простыми стратегиями |
| Скрипт оценки | Команда для воспроизведения таблицы и отчёта с зафиксированными данными, артефактом и настройками |
| Примеры запросов | Рабочие JSON-запросы и ответы для `WORKING_CAPITAL` и `EQUIPMENT`, включая подтверждённые нулевые поступления |
| Кредитный профиль | Соответствие признаков датасету; примеры `AVAILABLE` без просрочек и с просрочками, `NO_HISTORY`; проверка дат, сумм и отсутствия автоматического нулевого риска |
| Замеры времени | Условия запуска и фактическое время ответа на целевом компьютере; проверка бюджета HTTP-вызова 10 секунд |

Модель загружается до успешной проверки `/health/ready`, а не на каждом запросе. Порог в HTTP-ответ скоринга не добавляется: результаты его подбора передаются отдельно до включения модели в кредитную политику.

## 7. Интеграция и версии

Java-политика фиксирует `policyVersion`, `expectedModelVersion`, `featureSchemaVersion` и `riskCutoff`.

Текущая схема признаков — `2` (Scoring API 0.2.0). Версия `1` не содержит кредитного профиля и не подходит для текущего контракта. Изменение набора признаков требует обновлённого артефакта/версии модели, preprocessing и оценки порога. `demo-risk-v2` в примерах — синтетическое обозначение формата, не готовый артефакт.

1. ML передаёт артефакт, отчёт и рекомендуемый численный порог.
2. Команда проверяет результаты и фиксирует связку версии модели и политики для MVP.
3. Бэкенд применяет закреплённый порог и сохраняет связку версий с каждым рассмотрением.
4. Изменение модели или preprocessing требует новой версии модели и повторной оценки порога.
5. Ответ неожиданной версии модели не используется для кредитного решения. Старый порог автоматически на новую модель не переносится.

## 8. Открытые вопросы и ответственность

| Вопрос | Что требуется | Ответственный |
|---|---|---|
| Датасет и целевой исход | Источник, разметка, период наблюдения, применимость к бизнес-кредитам | ML |
| Достаточность признаков | Подтверждение работы по текущему API либо конкретный список необходимых изменений | ML + бэкенд |
| Кредитный профиль | Использование признаков схемы `2`, пригодность данных и preprocessing для `AVAILABLE`/`NO_HISTORY`; подготовка синтетических отчётов | ML + бэкенд |
| Поддержка двух продуктов | Подтверждение применимости общей модели и ограничения по каждому продукту | ML |
| Численный порог | Таблица кандидатов, выбранный порог и итоговый тестовый отчёт по критерию `10:1` | ML; связку политики фиксирует команда |
| Качество и калибровка | Фактические результаты и ограничения; отсутствие результатов обозначается явно | ML |
| Работа на целевом ПК | Артефакт, запуск, ресурсы и измеренное время ответа | ML + бэкенд |
| Подтверждённые нулевые поступления | Корректная обработка нуля без деления на ноль и подмены значения; рабочий пример ответа модели | ML |
| Выдача и погашение | Согласованные описания для карточек и решения; расчёт ежемесячного платежа текущий API не задаёт | Product/аналитик + бэкенд |
| Дополнительные уточнения | Новые правила за пределами `ZERO_INFLOW_CONFIRMATION` добавляются с конкретным вопросом, форматом ответа и условием продолжения | Product/аналитик + команда |
