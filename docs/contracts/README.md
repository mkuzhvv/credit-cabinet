Контракты взаимодействия фронтенда, Java-бэкенда, скоринга и LLM. Версия 0.1.0 от 22.10.2026. Реализация API ещё не создана.

Оба OpenAPI-файла самодостаточны: внешних `$ref` нет. Примеры встроены в спецификации; для LLM лежат в [examples/](llm/examples/product-request.json). Версия OpenAPI — 3.1.1, JSON Schema — 2020-12. Версия контрактов — 0.1.0.

## Общие соглашения

| Данные | Решение |
|---|---|
| JSON | camelCase; неизвестные поля запросов отклоняются |
| Идентификаторы | UUID |
| Время события | ISO 8601, UTC с `Z` |
| Деньги | Строка в RUB, ровно 2 знака: `"500000.00"`; без запятых, экспоненты и ведущих нулей |
| Срок | Целые месяцы |
| Продукт | Строковый код из каталога; MVP: `WORKING_CAPITAL`, `EQUIPMENT` |
| Версия заявки | Целое `version`; в изменениях — `expectedVersion` |
| Ошибка | `application/problem+json`: `type`, `title`, `status`, `code`, `requestId`, при необходимости `errors` |

Строки с пользовательским текстом не могут состоять только из пробелов. Клиенты не разбирают `title` и `message` для ветвления: используют коды. Неизвестные дополнительные поля ответа игнорируются; изменение смысла поля, обязательности входа или набора состояний требует совместного обновления контракта и клиентов.

## API фронтенда

Базовый путь — `/api/v1`. Каталог, заявки и чат требуют демосессии.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/csrf` | CSRF-токен; доступно анонимной сессии |
| POST | `/demo/session` | Автоматический вход в серверный демоаккаунт |
| GET | `/me` | Пользователь и компания |
| GET | `/products` | Действующие продукты и условия |
| POST | `/applications` | Новый черновик, `201` |
| GET | `/applications` | Страница доступных заявок |
| GET | `/applications/{applicationId}` | Форма, состояние и результат |
| PUT | `/applications/{applicationId}/form` | Полная замена формы |
| POST | `/applications/{applicationId}/submit` | Принятое рассмотрение, `202` |
| POST | `/applications/{applicationId}/retry` | Принятый технический повтор, `202` |
| POST | `/assistant/conversations` | Новый диалог, `201` |
| GET | `/assistant/conversations/{conversationId}/messages` | История по `sequence` |
| POST | `/assistant/conversations/{conversationId}/messages` | Вопрос и ответ LLM, `200` |

### Начало сессии

1. `GET /csrf` создаёт анонимную HTTP-сессию и возвращает `token`, `headerName`.
2. `POST /demo/session` отправляется с этой cookie и `X-CSRF-TOKEN`. Тело отсутствует.
3. После входа снова вызывается `GET /csrf`: предыдущий токен сбрасывается.
4. Все изменяющие запросы отправляют актуальную cookie и CSRF-токен.

Cookie — `JSESSIONID`, `HttpOnly`, `Path=/`, `SameSite=Lax`; `Secure` включается при HTTPS. JWT и экран входа отсутствуют. Другой UUID в запросе не даёт права на чужую заявку.

Предпочтительный запуск — один origin через frontend/reverse proxy. При разных origin браузер отправляет cookie с `credentials: include`, а сервер разрешает конкретный origin и credentials. После потери сессии фронтенд восстанавливает контекст и читает состояние; изменение с неизвестным исходом не повторяется новым ключом.

### Форма и версии

- Создание принимает только `productCode`. Пользователь, компания и условия определяются сервером.
- `PUT .../form` передаёт все поля `form`; `null` очищает значение. Неполный черновик допустим.
- Для оборотного кредита `equipment=null`. Для оборудования при отправке нужны название и положительная стоимость покупки.
- При отправке обязательны положительная сумма, срок и оба финансовых показателя; нулевые поступления или расходы не подменяются пропуском. Лимиты проверяются по продукту.
- В `NEEDS_INFO` можно менять только запрошенные поля. Прочие значения полного `form` остаются прежними.
- Автосохранение выполняется последовательно. Перед отправкой фронт ждёт успешного сохранения последнего ввода.
- `version` меняется и при изменении состояния. Конфликт — `409 VERSION_CONFLICT`; фронт не теряет локальный несохранённый ввод.
- `allowedActions` отражает права и состояние, а не полноту формы и не вероятность одобрения.

`submit` передаёт `expectedProductTermsVersion`: если условия изменились, сервер возвращает `409 PRODUCT_TERMS_CHANGED`. Фронтенд показывает новые условия и отправляет новую команду после действия пользователя.

### Фоновое рассмотрение

`submit` атомарно сохраняет снимок, `assessmentId`, состояние и задание. `202` подтверждает приём, не кредитное решение. Ответ содержит `statusUrl` и `pollAfterSeconds` (в примере 2 секунды).

GET заявки возвращает `200` для всех шести состояний. В `APPROVED`/`DECLINED` присутствует решение; в `NEEDS_INFO` — непустой список полей; в `TECHNICAL_HOLD` — техническая ошибка и действие `RETRY`. В YAML эти зависимости ограничены схемой.

После выхода из `CHECKING` или ухода со страницы опрос прекращается. Технический повтор использует прежние данные и условия, но новый `assessmentId`. Изменение формы, продукта и новая подача готового решения в этот повтор не входят.

### Повторы команд

`Idempotency-Key` обязателен для создания заявки, отправки, повтора, создания диалога и отправки сообщения. Один UUID на одно действие; при сетевом повторе используется тот же UUID и тело.

- Область ключа: текущий пользователь + компания + операция + ресурс. Смена сессии того же пользователя не сбрасывает ключ.
- Тот же ключ и тело возвращают исходный успешный результат. Другое тело — `409 IDEMPOTENCY_KEY_REUSED`.
- После проверки доступа повтор ищется до проверки `expectedVersion`.
- Успешный результат хранится минимум 24 часа в PostgreSQL. После этого срока безусловный повтор создания не обещается.
- Исходное `202` может описывать уже завершённую попытку; актуальное состояние читается через GET.
- Другой ключ не обходит ограничение одной активной проверки.

### Чат

Java владеет историей. Фронт передаёт текст и указатели контекста; не пересылает историю, каталог и финансовую анкету как достоверные данные.

Один активный запрос на диалог. При занятости — `409 CONVERSATION_BUSY` или `OPERATION_IN_PROGRESS`. Генерация идёт вне транзакции. Пара USER+ASSISTANT сохраняется атомарно после корректного ответа; при ошибке полупара не добавляется. Фронт сохраняет введённый текст до успеха.

Успешный повтор ключа не вызывает модель. После ошибки генерации допускается повтор того же ключа; контекст до первого успеха собирается заново. История возвращается по возрастанию `sequence`, с `afterSequence` и `limit`. В MVP ответ целиком, без streaming.

## Скоринг

Java вызывает `POST /internal/v1/assessments` обычным синхронным HTTP из фонового обработчика. Браузер не вызывает Python; пользовательская cookie туда не передаётся. Для MVP сервис доступен только во внутренней сети, отдельной схемы аутентификации в этом контракте нет.

- Все признаки типизированы и взяты из сохранённого снимка. Произвольный `Map<String, Object>` не используется.
- Python выполняет preprocessing и кодирование под модель, не читает БД Java и не запрашивает дополнительные данные у фронтенда.
- `assessmentId` сохраняется при транспортном повторе одной попытки; новая проверка получает новый ID.
- Возвращаются оценка и версия модели; `APPROVED`/`DECLINED`, ставка и порог отсутствуют.
- Java проверяет совпадение `assessmentId`, версию схемы и ожидаемую версию модели. Новый артефакт модели получает новую версию; порог политики нельзя незаметно переносить на другую модель.
- `riskScore` — конечное число `[0,1]`, больше означает больший риск. Без отдельного подтверждения калибровки значение не считается вероятностью дефолта (PD).
- `400`/`422` от Python — ошибка обмена/признаков для Java. Автоматически превращать их в `NEEDS_INFO` или отказ нельзя.
- `/health/live` проверяет процесс; `/health/ready` — загруженную модель, схему и поддерживаемые продукты. Модель не загружается на каждом запросе.

В MVP модель должна поддерживать оба продукта. Java не запускает оценку для продукта или схемы, поддержку которых не подтверждает readiness сервиса.

## Определения и параметры v0.1

| Пункт | Определение |
|---|---|
| Период финансов | 12 полных календарных месяцев до месяца создания черновика. Границы выдаёт сервер и сохраняет |
| Поступления | От деятельности бизнеса, без новых кредитов, вложений собственника и переводов между своими счетами |
| Расходы | Регулярные расходы, налоги и существующие обязательства; без будущего платежа по новой заявке и внутренних переводов |
| Оборудование | `name` и `purchasePrice` обязательны при отправке; в скоринг передаётся цена, не свободный текст названия |
| Возраст бизнеса | Полные месяцы от даты регистрации на `asOfDate`; источник — демопрофиль компании |
| Бюджеты HTTP | Скоринг 10 секунд; генерация ответа LLM 60 секунд. ML проверяет достижимость на целевом ПК |
| Чат | История сохраняется; атомарная пара вопрос+ответ; один активный запрос; без streaming |

Для первой демонстрации нужен профиль с полной 12-месячной историей. Для поддержки более молодого бизнеса требуются согласованные изменения определения периода и схемы признаков. Выдуманные данные и деление неполного периода на 12 недопустимы.

**Не назначены:** реальные значения условий двух демопродуктов, порог риска, формула кредитной политики и конкретный триггер `NEEDS_INFO`. Числа каталога и решения в примерах — фикстуры для проверки формы сообщений. Пример уточнения названия оборудования иллюстрирует формат и не утверждает существование проверки его смысла.

Порог и правило на его границе остаются в Java-политике; их нет в API Python. Эта версия не задаёт расчёт ежемесячного платежа: при одобрении возвращаются сумма, срок, ставка и описание погашения.

## Ответственность команды

1. Фронтенд: операции, форма, состояния, восстановление, cookie/CSRF, ошибки и повторы.
2. ML-скоринг: смысл и достаточность признаков, направление оценки, версия, ошибки и время ответа.
3. ML-LLM: [требования ассистента](llm/README.md), два полных примера и 20 контрольных вопросов.
4. Аналитик: определения финансовых полей, паспорта продуктов, причины и случай уточнения.

Изменения контрактов согласуются с разработчиками затронутых компонентов и сопровождаются обновлением схем и примеров.

## Проверка при подготовке v0.1

- Оба OpenAPI-документа прошли `openapi-spec-validator 0.7.2`.
- JSON-схемы и примеры проверены `jsonschema 4.23.0` в режиме 2020-12, включая форматы UUID и дат.
- Проверены ссылки, шесть состояний, согласованность версий и ID в последовательности создания/сохранения/отправки/повтора.
- 26 негативных проверок отклоняют неверные деньги, несовместимые состояния, неполные данные рассмотрения, лишние команды LLM и недопустимый риск.
- Четыре примера LLM и входы 20 контрольных вопросов соответствуют схемам. Модели и реальные серверы не запускались; качество ответов и время работы должен подтвердить ML-прогон.

Нормативные источники: [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html), [HTTP 202](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted), [Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html), [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).
