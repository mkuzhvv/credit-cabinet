# Кредитный профиль MVP

Решения обновлены 24.10.2026. Документ определяет источник кредитной истории, внутреннюю границу Java, данные скоринга и правила сохранения. Реализация провайдера и тестовые данные добавляются при написании кода.

## 1. Границы

- Java автоматически получает синтетический кредитный профиль компании. Пользователь его не заполняет и не редактирует.
- `CreditHistoryProvider` реализуется внутри Java как `DemoCreditHistoryProvider`; отдельный микросервис и реальное подключение к БКИ в MVP не нужны.
- Демоисточник содержит подготовленные профили по `companyId` и сценарии технических сбоев. Используются только синтетические данные; реальный запрос в БКИ и согласие на него не имитируются как уже выполненные действия.
- Текущая просрочка из профиля проверяется Java и даёт CURRENT_OVERDUE_DEBT до ML. Прошлые погашенные просрочки и NO_HISTORY остаются признаками модели, без отдельного автоматического отказа.
- Состояния заявки и форма сохраняются. Полный отчёт и его показатели в текущий API фронтенда и в LLM не передаются.

## 2. Внутренний контракт Java

`CreditHistoryProvider.getCreditHistory(companyId)` возвращает типизированный `CreditHistoryReport` либо техническую ошибку. `companyId` берётся из сохранённой заявки после проверки доступа, не из отдельного клиентского поля.

| Поле отчёта | Тип / значение | Назначение |
|---|---|---|
| `schemaVersion` | Строка `1` | Версия внутреннего отчёта, независима от версии признаков ML |
| `companyId` | UUID | Компания, для которой получен профиль |
| `source` | `DEMO_BKI` | Явная маркировка синтетического источника |
| `sourceVersion` | Непустая строка | Версия набора демонстрационных данных |
| `reportId` | UUID | Идентификатор отчёта в источнике |
| `receivedAt` | UTC timestamp с `Z` | Когда Java получила отчёт |
| `profile` | `CreditHistory` из [Scoring OpenAPI](contracts/scoring.openapi.yaml) | Данные для модели |

Все поля обязательны. Java проверяет принадлежность компании, типы, даты и согласованность данных до сохранения и вызова ML. Отсутствие записи компании в демоисточнике означает ошибку источника, а не доказанное отсутствие кредитной истории.

### Показатели `profile`

| Поле | Определение |
|---|---|
| `status` | `AVAILABLE` — согласованные сведения получены полностью; `NO_HISTORY` — проверка завершена, кредитных записей нет |
| `asOfDate` | Дата состояния обязательств по источнику; не позднее UTC-даты `receivedAt` |
| `delinquencyPeriod` | 12 полных календарных месяцев перед месяцем `asOfDate`, границы включительно и `months=12` |
| `totalOutstandingDebt` | Остаток задолженности по кредитным обязательствам в отчёте на `asOfDate`, включая просроченную часть |
| `monthlyDebtPayment` | Сумма ежемесячных платежей по действующим кредитным обязательствам в отчёте на `asOfDate` |
| `overdueDebtAmount` | Просроченная часть общей задолженности на `asOfDate`; не больше `totalOutstandingDebt` |
| `maxDaysPastDueLast12Months` | Максимальное число полных дней просрочки, наблюдавшееся в `delinquencyPeriod`; при отсутствии просрочек — 0 |

Денежные показатели — неотрицательные строки RUB с двумя знаками после точки. Число дней — неотрицательное целое. Просрочка могла начаться до указанного периода, поэтому число дней не ограничивается длиной периода.

При `AVAILABLE` все четыре показателя заполнены; наличие кредитных записей не означает хорошую историю. Погашенные кредиты могут давать нулевую текущую задолженность и ненулевой исторический показатель просрочки.

При `NO_HISTORY` все четыре показателя равны `null`; даты и период присутствуют. ML использует отдельное кодирование отсутствия истории, не трактует его как положительную историю и не присваивает автоматически нулевой риск. Неполный отчёт не становится `NO_HISTORY`.

`delinquencyPeriod` относится к дате кредитного отчёта и может отличаться от `reportingPeriod` формы, который закреплён при создании черновика. Эти даты не сдвигаются молча при повторе. `monthlyDebtPayment` — отдельный признак; его не прибавляют повторно к `averageMonthlyOutflow`, где существующие обязательства уже учтены.

## 3. Порядок обработки и снимки

1. `submit` сохраняет исходные сведения, условия и подтверждения в неизменяемый `input_snapshot`; новая попытка обычно ещё не содержит `credit_history_snapshot`.
2. Обработчик сначала применяет возраст и банковские требования продукта. При раннем отказе источник и ML не вызываются; подтверждение нуля проверяется позже.
3. Если успешный отчёт ещё не сохранён, обработчик вне транзакции вызывает провайдер с конечным бюджетом времени.
4. После проверки отчёта в короткой транзакции проверяет актуальность попытки, токен и срок захвата; однократно записывает весь `CreditHistoryReport` в `credit_history_snapshot`. Сохранённый отчёт не заменяется новым.
5. По сохранённому AVAILABLE проверяет overdueDebtAmount: положительная текущая просрочка даёт DECLINED/CURRENT_OVERDUE_DEBT без ML. NO_HISTORY проходит этот фильтр без подстановки сумм.
6. После этого проверяет ZERO_INFLOW_CONFIRMATION: при неподтверждённом нуле завершает NEEDS_INFO, отчёт остаётся сохранённым.
7. Иначе собирает ScoringFeatures схемы 3 из input_snapshot и credit_history_snapshot.profile и вызывает Python вне транзакции.
8. Java проверяет ответ, применяет порог и фиксирует итог с проверкой актуальности и захвата.

`credit_history_snapshot` добавляется в существующую `credit_assessment`; новых таблиц нет. При наличии `risk_score` успешный кредитный профиль обязателен. При раннем отказе по возрасту/банковским требованиям и сбое источника снимок может отсутствовать. При NEEDS_INFO и отказе по текущей просрочке отчёт уже сохранён.

### Повторы

- При повторном выполнении той же попытки уже сохранённый отчёт используется без нового получения.
- Технический `retry` создаёт новую попытку с теми же исходными данными и копией ранее сохранённого отчёта, если он есть. `receivedAt`, даты и идентификатор отчёта не обновляются.
- Если предыдущая попытка не получила валидный отчёт, `retry` пробует получить его; исходные данные заявки и параметры политики остаются закреплёнными.
- Продолжение после `NEEDS_INFO` создаёт новое рассмотрение с исправленными или подтверждёнными данными. Профиль получают для этой новой попытки; произвольный отчёт из более ранней истории заявки не подбирается.
- Запоздалый ответ после потери захвата не сохраняется. После завершения попытки оба снимка неизменяемы.

## 4. Ошибки

| Ошибка провайдера | Результат заявки | Вызов ML |
|---|---|---|
| Источник недоступен или демопрофиль компании не настроен | `TECHNICAL_HOLD`, `CREDIT_HISTORY_UNAVAILABLE` | Нет |
| Истёк бюджет получения | `TECHNICAL_HOLD`, `CREDIT_HISTORY_TIMEOUT` | Нет |
| Неверные типы, неполные показатели, чужая компания, некорректные даты или противоречивые суммы | `TECHNICAL_HOLD`, `CREDIT_HISTORY_INVALID_RESPONSE` | Нет |
| Успешный отчёт `NO_HISTORY` | Обычное рассмотрение по модели и политике | Да |

`UNAVAILABLE` не является значением `profile.status` и не отправляется в Python. Техническая ошибка не заменяется нулевыми суммами, положительной историей или кредитным отказом. Данные об ошибке сохраняются в результате попытки, не как успешный отчёт.

Фронт получает существующий `ApplicationView` с `processingError` и доступным `RETRY`; отдельного экрана ввода истории и нового состояния заявки нет.

В модели пяти продуктов расчётный финансовый период 3/6/12 месяцев не меняет 12-месячный период просрочек отчёта. Внутренний формат CreditHistoryReport остаётся schemaVersion=1; схема исходного input_snapshot — 2, ScoringFeatures — 3. Базовый тип CreditHistory допускает текущую просрочку для провайдера, но ScoringFeatures дополнительно требует overdueDebtAmount=0.00 при AVAILABLE.

## 5. Обязанности ML

- Поддержать обязательный `creditHistory` в `featureSchemaVersion=3`, все пять продуктов и оба успешных статуса профиля.
- Описать соответствие показателей датасету, единицы, периоды и preprocessing. Простое принятие новых полей JSON без их использования не считается поддержкой признаков.
- Для `NO_HISTORY` описать отдельное кодирование отсутствия истории и проверить конечный результат без подмены значений хорошей историей.
- Данные о погашении новой заявки из будущего не входят в признаки. Источник данных, целевой исход, качество и ограничения фиксируются в паспорте модели.
- Если модель обучается на синтетических данных, её демонстрационное качество не объявляется подтверждением пригодности для реального кредитования.
- Повторно оценить порог для версии модели с расширенными признаками; старый порог автоматически не переносится.

## 6. Проверки при реализации

| Проверка | Ожидаемое поведение |
|---|---|
| Полный профиль без просрочек / с исторической погашенной просрочкой | В ML переданы фактические показатели; прошлые просрочки не дают отдельного автоматического отказа |
| Текущая просрочка >0 | DECLINED/CURRENT_OVERDUE_DEBT до ML и уточнения нуля |
| `NO_HISTORY` с четырьмя `null` | Статус передан ML отдельно; результат определяет модель и политика |
| `AVAILABLE` с `null`, `NO_HISTORY` с числами, отрицательные суммы, чужой `companyId`, неверный период | Ошибка контракта; ML не вызывается |
| Источник недоступен или завис | Соответствующая ошибка и `TECHNICAL_HOLD`, доступен повтор |
| Сбой ML после сохранения отчёта | `retry` использует прежний отчёт, даже если демоисточник уже изменён |
| Сбой до получения валидного отчёта | `retry` получает отчёт заново |
| Перезапуск после записи профиля и до вызова ML | Восстановленный обработчик использует сохранённый профиль |
| Старый обработчик вернулся после истечения захвата | Не записывает отчёт и не применяет решение |
| Ранний отказ по возрасту/счёту/регулярности | Провайдер и ML не вызываются |

Изолированные примеры проверки и сквозные сценарии используют фиксированные синтетические профили. Изменение источника между техническими повторами не меняет уже рассмотренные сведения.
