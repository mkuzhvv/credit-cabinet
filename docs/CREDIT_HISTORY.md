# Кредитная история

## 1. Источник и граница интеграции

Java получает внутренний [CreditHistoryReport](../backend/src/main/java/com/creditcabinet/credit/credithistory/CreditHistoryReport.java) через [CreditHistoryProvider](../backend/src/main/java/com/creditcabinet/credit/credithistory/CreditHistoryProvider.java).

Текущая реализация [DemoCreditHistoryProvider](../backend/src/main/java/com/creditcabinet/credit/credithistory/DemoCreditHistoryProvider.java) читает синтетические профили из [demo/credit-history](../backend/src/main/resources/demo/credit-history/). Реальный БКИ не подключён. Новый источник должен преобразовывать внешний формат в этот внутренний отчёт; демообозначение источника проверяется внутри демоадаптера.

[CreditHistoryReportValidator](../backend/src/main/java/com/creditcabinet/credit/credithistory/CreditHistoryReportValidator.java) проверяет принадлежность компании, версию, обязательность, даты, период и согласованность показателей.

## 2. Формат отчёта

Метаданные: `schemaVersion="1"`, companyId, source, sourceVersion, reportId, receivedAt. `profile` содержит:

| Поле | Значение |
|---|---|
| status | AVAILABLE — сведения есть; NO_HISTORY — источник подтвердил отсутствие записей |
| asOfDate | Дата состояния обязательств, не позже UTC-даты receivedAt |
| delinquencyPeriod | 12 полных месяцев перед месяцем asOfDate, включая обе границы |
| totalOutstandingDebt | Текущая общая задолженность, включая просроченную часть |
| monthlyDebtPayment | Ежемесячные платежи по действующим обязательствам |
| overdueDebtAmount | Текущая просроченная часть, не больше общей задолженности |
| maxDaysPastDueLast12Months | Максимальная длительность просрочки в указанном периоде |

При AVAILABLE все четыре показателя заполнены; нулевой текущий долг возможен, например для погашенных кредитов. При NO_HISTORY все четыре равны null. Неполный или недоступный отчёт не становится NO_HISTORY.

Деньги — неотрицательные строки RUB с двумя десятичными знаками. Дни — неотрицательное целое. Исторический период всегда 12 месяцев и может отличаться от финансового периода анкеты 3/6/12 месяцев.

## 3. Демосценарии

Свойство `demo.credit-history.scenario` выбирается при запуске Java.

| Сценарий | Профиль или результат |
|---|---|
| DEFAULT | Базовый профиль соответствующей компании |
| ACTIVE_LOANS | Действующие кредиты без текущей просрочки |
| REPAID_LOANS | Погашенные обязательства |
| PAST_OVERDUE | Просрочка в прошлом |
| CURRENT_OVERDUE | Положительная текущая просрочка |
| NO_HISTORY | Подтверждённое отсутствие кредитной истории |
| HIGH_DEBT_LOAD | Крупные действующие обязательства |
| UNAVAILABLE | Техническая недоступность источника |
| TIMEOUT | Технический таймаут источника |

Для проверки другого сценария в существующий блок `environment` сервиса `backend` в [compose.yaml](../compose.yaml) добавляется, например, `DEMO_CREDIT_HISTORY_SCENARIO: CURRENT_OVERDUE`. После этого повторно запускается общий запускатор. Одного `restart` недостаточно для изменения окружения существующего контейнера. Для возврата используется DEFAULT или удаление переопределения с обновлением контейнера.

Сценарий применяется ко всем новым получениям отчёта этим экземпляром Java. Это не переключатель пользователя в браузере и не набор новых компаний. Уже сохранённый отчёт не заменяется после смены сценария; для независимой проверки создаётся новая заявка.

HIGH_DEBT_LOAD сам по себе не задаёт обязательный отказ: текущая формальная проверка учитывает расходы, в которых уже должны быть отражены платежи. Историческая просрочка также не равна текущей просрочке.

## 4. Порядок обработки

После принятия submit обработчик сначала проверяет возраст и банковские требования продукта. При раннем отказе отчёт не запрашивается.

Если отчёта ещё нет, Java получает его вне транзакции с бюджетом 5 секунд, валидирует и однократно сохраняет в `credit_assessment.credit_history_snapshot` под действующим токеном захвата.

Положительная текущая просрочка даёт `DECLINED / CURRENT_OVERDUE_DEBT` до уточнения нуля и Python. NO_HISTORY проходит этот фильтр без подстановки нулей. Затем проверяется необходимость уточнения и вызывается скоринг.

Полный отчёт сохраняется вместе с источником, ID и датами. Python получает профиль, а не технические метаданные источника. Помощник не получает кредитный отчёт.

## 5. Повторы и ошибки

- Повторное исполнение той же попытки использует сохранённый отчёт.
- Технический retry копирует имеющийся отчёт в новую попытку вместе с исходными датами и reportId.
- Если валидный отчёт раньше не был получен, retry получает его.
- Новый submit после уточнения получает отчёт для новой попытки.
- Ответ после потери токена/срока захвата не записывается.

Ошибки `CREDIT_HISTORY_UNAVAILABLE`, `CREDIT_HISTORY_TIMEOUT`, `CREDIT_HISTORY_INVALID_RESPONSE` завершают попытку в TECHNICAL_HOLD. Они не создают фиктивный профиль и не означают плохую историю.

Сохранение снимка и итогов подробнее описано в [разборе обработки](BACKEND_WALKTHROUGH.md) и [схеме БД](DATABASE_SCHEMA.md).
